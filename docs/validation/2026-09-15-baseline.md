## Latency measurement method and caveats

Full method is documented in the `measure_latency.py` module docstring; summary:

- **What is timed:** wall-clock time around a single `requests.post(...)` call (no session/connection pooling — a fresh TCP connection per request, matching how `device/device.py` and `gateway/app/cloud_client.py` actually issue requests), from just before the call to just after the response body is fully read.
- **Two targets:** `POST /device-data` on the gateway (full device→gateway→cloud path) and `POST /data` sent directly to the cloud by the measurement script (isolates the gateway→cloud leg). `device_data − cloud_data` is only an **approximation** of gateway-added overhead: the two measurements are not made from the same client process (the gateway's own outbound call to the cloud is not directly observed), so the two legs are not perfectly comparable.
- **Sampling:** 5 discarded warm-up requests, then 50 timed samples per target, strictly sequential (one request in flight at a time; no concurrency).
- **Failure handling:** a `requests.exceptions.RequestException` (timeout, connection refused, etc.) counts as a failure and is excluded from the latency statistics; a non-2xx HTTP response is still a valid timed observation, not a failure. `measure_latency.py` exits non-zero if any target has zero successful samples or any recorded failure.
- **Excluded by design:** any network hop beyond loopback, concurrent/sustained load, container or Docker-network overhead, and server cold start (servers are already up and past their first request before timing begins). The cloud's in-memory list grows by one entry per warm-up/sample call and by the functional-check readings before it, but `GET /data` retrieval time itself is not measured.

## Residual uncertainty

- **Run-to-run variance is large relative to the absolute numbers.** `device_data` mean latency was 4.084 / 2.383 / 3.187 ms across attempts 1–3 (up to a ~1.7× spread) on the same machine within about ten minutes, most plausibly interpreter/OS warm-up beyond the script's fixed 5-request warm-up budget, other processes on a shared development laptop (including other agents' concurrent work in this same repository), and general scheduling noise. Treat the absolute millisecond figures as **order-of-magnitude**, not a precise SLA; the more stable signal across all three attempts is that the cloud leg alone (`cloud_data`, ~0.9–1.1 ms mean) is consistently 2–3× cheaper than the full device→gateway→cloud path (`device_data`, ~2.4–4.1 ms mean), consistent with the gateway adding one extra HTTP hop plus its own validation/logging.
- **Python 3.13.12 vs. the containers' 3.12** is an unverified difference; interpreter-level performance and any 3.12/3.13-specific behavior differences in FastAPI/Starlette/uvicorn are not measured here.
- **Transitive dependency versions inside the container image are unverified.** Only the top-level pins (`fastapi==0.115.6`, `uvicorn[standard]==0.32.1`, etc.) are guaranteed to match; `starlette`, `pydantic`, `h11`, `uvloop`, and `httptools` versions actually resolved during a `python:3.12-slim` build were not checked, since the daemon is unavailable to build the image.
- **Local uvicorn process vs. Docker Compose deployment** is a materially different runtime: no container overlay network, no image-layer filesystem, no `depends_on` startup-order race, no resource limits. None of that is exercised by this baseline; the README's own manual checks against the Compose stack remain the reference for that scenario and have not themselves been re-run as part of this record.
- **This baseline ran in a repository being edited concurrently by other agents; this record is accurate as of attempt 3's completion, not as of "now."** Attempts 1–2 ran against source exactly at HEAD `1c72c3f` (confirmed via `git diff --stat` at orientation time). Before attempt 3, `gateway/app/metrics.py` gained additional metric declarations (unused by this baseline); attempt 3 was run afterward and confirmed the checks and endpoints this baseline exercises (`cloud_forward_failures_total`, and every endpoint under test) still behaved identically. While finishing this write-up, a further `git diff --stat` (after attempt 3 had already completed) showed `gateway/app/models.py` and `cloud/app/models.py` had also since gained a shared temperature range validator (`-40.0`–`60.0` °C, via a new `Field(ge=..., le=...)`). Every temperature value this baseline sends (`22.5`, `19.9`, and randomised values in `15.0`–`30.0` for the latency samples) falls inside that range, so the recorded `PASS` results would not be expected to change — but this was **not** re-verified with a fourth run, and a concurrent repository should be assumed to keep moving after this record is written.
- **Small sample of three runs on one idle-ish machine.** No statistical claim is made beyond what these attempts show; a larger number of repeated runs (or a higher `--samples` value) would be needed to characterize variance more rigorously.
- **`scripts/baseline/last-baseline.json` is a generated, overwritten artifact**, not hand-maintained; it currently reflects attempt 3 above. It is untracked (new file, alongside the rest of `scripts/`) — this record does not modify `.gitignore` and takes no position on whether it should eventually be tracked or ignored.
