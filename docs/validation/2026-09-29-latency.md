## Method

**What is timed.** The same quantity as [`measure_latency.py`](https://github.com/Rolko6/Software-Development-and-Maintenance-Project/blob/0d9f085a2895910871e1dadf10d9ef07ba88a8c0/scripts/baseline/measure_latency.py) and [`compare_latency.py`](https://github.com/Rolko6/Software-Development-and-Maintenance-Project/blob/0d9f085a2895910871e1dadf10d9ef07ba88a8c0/scripts/evaluation/compare_latency.py): one bare `requests.post` to `POST /device-data` (no `requests.Session`, so a new TCP connection per request), timed with `time.perf_counter()`, a monotonic clock, from just before the call to just after the body is read. The gateway returns its response only after the cloud has answered, so this is request-to-acknowledgement time. Requests are sequential, one in flight. Warm-up requests are sent first and discarded; the very first request after a container start always makes a handshake and is therefore always a warm-up.

**How each request is classified.** The script scrapes the gateway's `/metrics/` before and after every timed request, outside the timed window, and compares the counters:

| Class | Observed signal |
| --- | --- |
| `new_session` | `gateway_handshake_succeeded_total` rose during the request |
| `reused_session` | no handshake counter moved |
| `handshake_failed` | `gateway_handshake_started_total` rose without a success |
| `off` | the gateway reports `gateway_security_mode` `off` |

A response other than `200`, or an exception, is a failure. Failures are excluded from the latency statistics and listed by class and status code. Statistics: min, median, p95 (nearest rank, as in the existing scripts) and max, in milliseconds.

**How new sessions were forced.** The gateway renews a session 15 s before the expiry the cloud announced ([`client.py`](https://github.com/Rolko6/Software-Development-and-Maintenance-Project/blob/0d9f085a2895910871e1dadf10d9ef07ba88a8c0/gateway/app/crypto/client.py), `DEFAULT_REKEY_SKEW_SECONDS`), and the cloud's session lifetime is `CLOUD_ML_KEM_SESSION_TTL_SECONDS`.

- **Short TTL (main method).** With the cloud TTL at 10 s, every session is already inside the gateway's renewal window when it is created, so the gateway handshakes before every reading. Each sample moved `gateway_session_rekeys_total{reason="expired"}` by 1. Compared with a reused session, this adds exactly the handshake: `GET /secure/handshake`, ML-KEM-768 encapsulation, `POST /secure/handshake` and the key derivation. There is no idle gap, no retry and no rejected request.
- **Cloud restart (secondary).** In a stack with the default 300 s TTL, the script runs `docker restart` on the project's cloud container before each timed request and waits for `/health`; the restart and the wait are not timed. The gateway's next `POST /secure/data` gets a 404 for the forgotten session, the gateway handshakes again and resends. Each sample moved `gateway_session_rekeys_total{reason="forced"}` by 1. This adds the rejected `POST /secure/data` and a cloud process that has just started, on top of the handshake, so it is reported separately.

**Reused sessions** were measured with the default 300 s TTL: after the warm-up handshake no further handshake happened in either run. **Off mode** used `CLOUD_ML_KEM_MODE=off` and `GATEWAY_ML_KEM_MODE=off` with the same script; the gateway reported `off` and its handshake counters stayed at 0.

| --- | --- | --- | --- | --- | --- | --- |

Reading the numbers:

- A request that establishes a session took about 2.6 ms longer at the median than one reusing a session (5.9 against 3.3 ms). The gateway's own `gateway_handshake_duration_seconds` agrees: in the R1 short-TTL stack, 105 handshakes took 386 ms in total, a mean of 3.7 ms, and 96 of them finished within 5 ms.
- A reused session was about 0.4 ms slower at the median than off mode (3.3 against 2.9 ms), which covers the AES-GCM protection and the secure endpoint's extra work.
- The p95 and maximum values move between runs by more than the difference between reused-session and off-mode requests; the single 44.4 ms outlier in R1 reused was the last request of the run. At a load average around 10 on the host, the tails say more about the machine than about the code.
- The cloud-restart path took about 3 ms more than the short-TTL path at the median, consistent with the extra rejected `POST /secure/data` and a freshly started cloud process.

Cross-checks: the counter deltas were identical within each phase (every short-TTL sample: 1 handshake started, 1 succeeded, 1 `expired` rekey; every restart sample: the same with `forced`; every reused and off sample: no change). The cloud's log for the first enabled stack showed 41 `POST /secure/handshake` lines, matching 1 handshake on the stack's first request (a 5-request smoke check of the script before R1) plus 40 restarts; the last stack showed 110, matching its 10 warm-up and 100 timed handshakes and the gateway's `gateway_handshake_succeeded_total` of 110.

## Failures

No request failed in any latency phase: 0 of 1,440 timed requests returned anything other than `200`.

To check that failures are counted rather than lost, the cloud container was stopped for a separate 10-request probe. All 10 returned `502` and were classified `handshake_failed` (each request: 3 handshakes started, 3 `peer_unavailable` failures). They took 634 ms at the median and 652 ms at most, which is the gateway's retry budget (three attempts, 0.2 s and 0.4 s backoff), not a latency of the secure channel. The probe was run twice, the second time after the script gained its failure-timing fields; the first run also gave 10 × `502`, at 620–642 ms. The second, reported here, ran during a load spike (1-minute load average 36) caused by other work on the host.

## Limits

- The three measurements in this series (detection, recovery and delivery, latency) ran at the same time on one laptop. At about 11:00 UTC the latency run briefly overwrote the recovery run's untracked Compose override file with its own. It was restored from the recovery run's container settings a few minutes later. The recovery run's containers were created before the overwrite and kept ports 38000/38001, but whether any later recreation used the overwritten file cannot be fully ruled out.
- Other Compose stacks and agents were running on the host (load average 8–12, briefly 36). Medians differed between R1 and R2 by at most 0.81 ms; p95 and max were not.
- Client and servers share one machine; the network is Docker Desktop's port forwarding and a Compose bridge network, not a real link. The results say nothing about constrained devices or real networks.
- The short-TTL method makes every request a new session and puts up to about 100 short-lived sessions in the cloud's memory at once. It measures the cost of a handshake, not how often production traffic pays it: with the default 300 s TTL and the 15 s skew, the gateway renews roughly every 285 s, about once per 57 readings at the device's 5 s interval.
- The client opens a new TCP connection per request (as the existing scripts do), whereas the device keeps one `requests.Session`. Absolute values include connection setup.
- Classification scrapes `/metrics/` right before each request, so the gateway has always just served a request; this is the same for every class.
- A scripted second round first failed to recreate the stack in enabled mode. Its two phases labelled enabled actually ran in off mode (the gateway reported `off` and the script classified every request `off`), so they were discarded and re-run; only the re-runs are reported.
- Raw samples (JSON, 11–36 KB per phase) were kept outside the repository and are not committed.

## Reproducing

From the repository root, with an override file outside the repository that publishes the ports on 127.0.0.1 and sets `CLOUD_ML_KEM_SESSION_TTL_SECONDS: "${M4_CLOUD_TTL:-300}"` for the cloud:

```sh
DC="docker compose -p m4latency -f docker-compose.yml -f /path/to/override.yml"
$DC up -d --build cloud gateway              # enabled, TTL 300: reused sessions
python scripts/evaluation/measure_session_latency.py --compose-project m4latency \
  --label reused --samples 300 --warmup 10 --json-out /tmp/reused.json
python scripts/evaluation/measure_session_latency.py --compose-project m4latency \
  --label restart --force cloud-restart --samples 40 --warmup 2 --json-out /tmp/restart.json
M4_CLOUD_TTL=10 $DC up -d --force-recreate cloud gateway   # every request a new session
python scripts/evaluation/measure_session_latency.py --compose-project m4latency \
  --label new --samples 100 --warmup 10 --json-out /tmp/new.json
CLOUD_ML_KEM_MODE=off GATEWAY_ML_KEM_MODE=off $DC up -d --force-recreate cloud gateway
python scripts/evaluation/measure_session_latency.py --compose-project m4latency \
  --label off --samples 300 --warmup 10 --json-out /tmp/off.json
$DC down -v
```

`--gateway-url` and `--cloud-url` default to `http://127.0.0.1:48000` and `http://127.0.0.1:48001`. The script needs `requests`; `--force cloud-restart` also needs the `docker` CLI. It prints a summary table and writes the summary and every raw sample, with its counter deltas, to `--json-out`.
