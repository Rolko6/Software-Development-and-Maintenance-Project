## Behaviour before the change

Observed on 2026-09-28 against the running Compose stack built from `9bb782a`, sending hand-written bodies with `curl.exe` from Windows PowerShell:

| Sent | Gateway `POST /device-data` | Gateway log | Gateway metrics | Cloud `POST /data` |
| --- | --- | --- | --- | --- |
| `-127.0` | `422` | Only the uvicorn access line; no `device_id` | Unchanged: no `rejected_validation` series | `422`; `cloud_readings_rejected_total{reason="invalid_temperature"}` incremented |
| `85.0` | `422` | Same as above | Unchanged | Not sent to the cloud directly |
| `NaN` | `500 Internal Server Error` | Traceback ending `ValueError: Out of range float values are not JSON compliant: nan` in FastAPI's `request_validation_exception_handler` | Unchanged | `500`; the rejection counter was still incremented |

Cause: validation rejected the value correctly, but the `422` body echoes the rejected input, and `json.dumps` refuses to serialise `nan`, so building the error response raised. `GET /data` on the cloud held no out-of-range reading after these requests.

A second defect was found on the device side, first by reasoning and then by the regression test in `77f295f`: `requests` with `json=` raises `InvalidJSONError` (a `RequestException`) for a `NaN` payload, so a failed sensor read was never sent and was logged as `Failed to deliver ... error=Out of range float values are not JSON compliant`, as if the network were down.

Defects caught while writing the change:

- Fault rates that are exactly 1 were rejected: `0.33 + 0.56 + 0.11` is `1.0000000000000002` in floating point, and 2026 two-decimal combinations summing to 1 overflowed. The sum check now has a `1e-9` tolerance, with a regression test.
- A new test compared a `str` body with `bytes`; the test was corrected, not the code.

## Running stack with a faulty sensor

`docker compose -f docker-compose.yml -f monitoring/docker-compose.monitoring.yml up --build -d --force-recreate` with `TEMPERATURE_MODEL=ds18b20`, `FAULT_DISCONNECT_RATE=0.05`, `FAULT_POWER_ON_RESET_RATE=0.03`, `FAULT_NAN_RATE=0.05` and `FAULT_STUCK_RATE=0.01`, confirmed inside the device container with `env`. The stack ran for about 20 minutes on 2026-09-28 (19:42–20:05 UTC).

| Check | Observed |
| --- | --- |
| `docker compose config --quiet`, defaults | Exit 0; device resolves to `TEMPERATURE_MODEL: uniform` and every `FAULT_*` to `"0"` |
| Device log | `-127.00`, `85.00` and `nan` readings, each logged as `WARNING:app.runner:Gateway rejected reading ... status_code=422` |
| Gateway status codes returned to the device, before the diagnostic probe below | `179× 200`, `40× 422`, no `500` |
| Tracebacks or `500` in the whole gateway log | `0` |
| Gateway log for a rejection | `WARNING:app.main:Rejected reading from device 'legacy-sensor-001': invalid temperature` |
| Cloud `GET /data` | 241 readings stored, 0 outside −40…60 °C |
| Prometheus targets | `gateway` and `cloud` both `up` |
| `gateway_delivery_outcome_total` in Prometheus | `forwarded 242`, `rejected_validation 97`; the 97 includes 48 requests from the diagnostic probe |
| `rate(gateway_delivery_outcome_total[1m]) * 60` | `forwarded` around 9–12 per minute and `rejected_validation` around 0–2.7, together about 12 per minute at the 5-second interval; two spikes to 16 per minute are the diagnostic probe runs |

The observed rejection share, 40 of 219 gateway responses (18 %), is higher than the model predicts. The configured disconnect, reset and `NaN` rates add up to 13 %, but no fault is drawn while the sensor is stuck, so the expected share is lower: a follow-up simulation of the same configuration over 100,000 seeded readings gave 11.6 % (10.8–12.5 % per 5,000). In 200 windows of 220 simulated readings, 40 or more rejections occurred once, so the live result is possible but unusual. Every one of the 40 was a rejection of `legacy-sensor-001` in the gateway log. The device-side breakdown by fault value could not be recounted afterwards, because the stack, and with it the container logs, had already been removed. Whether this was chance or a difference between the live device and the unit-level model is open; a longer run with a fixed `RANDOM_SEED` would settle it.

## Open finding: `RemoteDisconnected` on valid readings

The device logged four `Failed to deliver` errors during the run. The first (`Max retries exceeded`, `19:42:26`) came before the gateway had started, the known best-effort startup ordering. The other three were valid readings failing with `('Connection aborted.', RemoteDisconnected('Remote end closed connection without response'))`.

- **Observed:** each of the three errors (`19:43:36`, `19:46:11`, `19:53:26` UTC) was followed five seconds later by the device's first request on a new source port in the gateway access log (`19:43:41`, `19:46:16`, `19:53:31`). The device reuses one `requests.Session`; the gateway's uvicorn 0.32.1 was confirmed to use `timeout_keep_alive = 5`, equal to the device's 5-second send interval. Two of the three errors followed a rejected reading.
- **Hypothesis, unconfirmed:** the gateway closes the idle keep-alive connection at the moment the device reuses it.
- **Not reproduced:** a probe replaying the device loop with one session (12 cycles at 5 s and 12 at 4 s, once from the host and once from inside the device container) got `422` on all 48 requests. With about 3 errors in 220 readings, 24 cycles per run may simply be too few.
- **Not established:** whether this also happened before this change. The session reuse and the 5-second interval predate it, but the original device was not run long enough to check.

Suggested follow-up, not implemented: run the unmodified `uniform` device for about 20 minutes and count the same error; if it recurs, raise the gateway's `--timeout-keep-alive` above the send interval or retry once on a reset connection, with a regression test.
