## What is genuinely strong

The project is well beyond a typical student prototype. The ML-KEM integration in
particular is surprisingly sophisticated:

- The **counter-poisoning DoS defense** in `SessionStore`
  (`cloud/app/crypto/sessions.py`) uses `check_counter` before decryption and
  `commit_counter` only after a ciphertext successfully authenticates. This is a real
  security subtlety — an unauthenticated counter advance could let an attacker poison
  the replay window and silently DoS later legitimate messages. It is correctly
  identified and handled.
- **HKDF key derivation**, bidirectional PSK MAC, and FIPS 203's implicit-rejection
  behaviour are all correctly understood and documented in
  `docs/security/ml-kem-integration.md`.
- The **nonce reuse invariant** (restart → fresh key → safe counter reset) is spelled
  out as a load-bearing guarantee and backed by a concrete argument in the design doc.
- Test suite breadth is solid: ~1,140 lines of per-service unit tests, plus ~2,500 lines
  across `tests/crypto/`, `tests/reliability/`, and `tests/protected_path/`.
- Validation records and AI evidence trail are unusually thorough for academic work.

## Areas worth investigating

### 1. Crypto metrics are wired but never called — known gap, wiring is missing

`cloud/app/metrics.py` defines six crypto counters/histograms:

- `CLOUD_HANDSHAKE_STARTED_TOTAL`
- `CLOUD_HANDSHAKE_SUCCEEDED_TOTAL`
- `CLOUD_HANDSHAKE_FAILED_TOTAL`
- `CLOUD_HANDSHAKE_DURATION_SECONDS`
- `CLOUD_CRYPTO_DECRYPT_FAILURES_TOTAL`
- `CLOUD_CRYPTO_ENCRYPT_FAILURES_TOTAL`

None of them are imported or called anywhere in `cloud/app/crypto/router.py`. The
same pattern holds on the gateway side. The project plan itself acknowledges this:
*"The handshake and encrypt/decrypt counters inside the crypto packages still read
zero."*

The definitions exist and the prometheus scrape config is in place; the only missing
piece is calling `.inc()` / `.observe()` at the right points in the handshake and
data endpoints.

### 2. `tests/crypto/`, `tests/reliability/`, and `tests/protected_path/` are not in CI

The CI workflow (`.github/workflows/ci.yml`) runs only three per-service pytest jobs
(`cloud`, `gateway`, `device`) plus the integration smoke test (`tests/integration/`).
No CI job runs the ~2,500 lines of root-level crypto, reliability, or protected-path
tests.

That means a regression in the ML-KEM handshake, session replay defense, or retry
reliability behaviour would not be caught automatically on every pull request. The
project's claim of automated CI does not cover these suites.

Adding a fourth matrix job (or a separate job) that installs `requirements-dev.txt`
at the root and runs `python -m pytest tests/crypto tests/reliability tests/protected_path`
would close this gap.

### 3. Stale comment at the top of `gateway/app/cloud_client.py`

Lines 1–2 of the file read:

```python
# Initially, this sends data normally.
# Later, this will become the place where ML-KEM is integrated.
```

ML-KEM is already integrated in that file. The comment describes an earlier state of
the code and is now misleading to a reader.

### 4. `wire.py` is manually duplicated in both services with no sync check

`cloud/app/crypto/wire.py` and `gateway/app/crypto/wire.py` are acknowledged
identical copies — both files say so in their headers. There is no automated check
enforcing they stay in sync. If someone edits one and not the other, the gateway and
cloud silently disagree on the wire protocol. Neither per-service test suite nor the
current CI would catch the divergence, because each service only imports its own copy.

A simple `diff` step in CI (or a shared package in a future refactor) would prevent
this class of silent breakage.

### 5. ML-KEM private key stored unencrypted on disk

`cloud/app/crypto/keys.py` (`KeyManager._load_or_generate`) writes the private key
as unencrypted PKCS8 DER and applies `chmod 600`. On a shared filesystem or a
compromised container image, the key is readable as plaintext. The design doc
acknowledges this (*"protect the file with filesystem permissions / a mounted secret
volume"*), but it is a real gap for any non-trivial deployment. Encrypting the key
at rest (e.g. with a passphrase or a secrets manager) is the natural next step.

### 6. `_reusing` wrapper accesses a private prometheus_client internal

Both `cloud/app/metrics.py` and `gateway/app/metrics.py` define a `_reusing` helper
that resolves duplicate-registration errors by calling
`REGISTRY._names_to_collectors.get(name)`. This accesses a private attribute of the
`prometheus_client` library. If the library changes its internal structure, this
breaks silently at import time. The reason the wrapper exists is sound (test isolation
— multiple test modules import the same `app.metrics` package), but it relies on an
undocumented internal.

### 7. No `healthcheck:` directives in `docker-compose.yml`

Documented as a known limitation. `depends_on` guarantees only that the container
process starts, not that the application inside it is ready. The `smoke-test.sh`
script polls `/health` to compensate, but a production or shared-environment
`docker compose up` can still see transient connection failures from the gateway or
device before the cloud is ready. Adding `healthcheck:` entries and
`depends_on: condition: service_healthy` would make startup reliable without
relying on the simulator's own retry loop.

### 8. No rate limiting or authentication on any endpoint

Anyone who can reach port 8000 can:
- Read all stored sensor data via `GET /data` (no authentication)
- Flood the gateway with arbitrary readings (no rate limiting)
- Observe the full ML-KEM encapsulation key and its fingerprint via
  `GET /secure/handshake`

This is appropriate for a prototype and is not listed as a design gap in the current
scope, but it is worth noting for any evaluation of the security posture.
