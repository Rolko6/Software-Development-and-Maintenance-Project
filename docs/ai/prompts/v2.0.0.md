## 1. What changed since v1.0.0

| Area | v1.0.0 | v2.0.0 |
| --- | --- | --- |
| Gateway→cloud link | Plaintext HTTP | ML-KEM-768 key establishment + AES-256-GCM, authenticated by a pre-shared key (`ML_KEM_PSK`); switched on in Compose |
| Device→gateway link | Plaintext HTTP | Unchanged, plaintext by design (the legacy device is the thing being preserved) |
| Device simulator | Single `device/device.py` | `device/app/` package: config, models, sensor, gateway client, runner |
| Reliability | Fixed health responses, unreported failures, inconsistent validation | Shared validation rules, bounded retry with backoff, real `/ready` checks, bounded storage, honest device logging |
| Observability | Basic metrics endpoint | Delivery, retry, validation, storage and duration metrics wired; Prometheus config; evaluation harness |
| Tests | None | Unit suites for all three services, Compose integration suite, ML-KEM known-answer, property and protected-path tests, docs-checker regression tests |
| CI/CD | None | `CI`, `Docs check` and `Publish images` GitHub Actions workflows |
| Documentation | README | Documentation index, project plan, decisions 0001–0002, security design, operations guides, validation records, AI prompt records |

The work was delivered through pull requests [#1](https://github.com/Rolko6/Software-Development-and-Maintenance-Project/pull/1), [#2](https://github.com/Rolko6/Software-Development-and-Maintenance-Project/pull/2) and [#3](https://github.com/Rolko6/Software-Development-and-Maintenance-Project/pull/3) into `develop`, then released from `develop` to `main`.

### Why this is a major version

Two changes are not backwards compatible for someone running v1.0.0 unchanged:

- **Compose now ships `CLOUD_ML_KEM_MODE=enabled` and `GATEWAY_ML_KEM_MODE=enabled`.** The gateway forwards every reading over the new `/secure/handshake` and `/secure/data` cloud endpoints instead of plaintext `POST /data`, and both services must share the same `ML_KEM_PSK`.
- **The device entry point moved** from `device/device.py` to the `device/app/` package (`python -m app`).

### Migrating from v1.0.0

- To get the v1.0.0 wire behaviour back, set `CLOUD_ML_KEM_MODE=off` and `GATEWAY_ML_KEM_MODE=off`. In `off` mode the services do not import the cryptographic code at all.
- The cloud still accepts plaintext `POST /data` in `enabled` mode, so existing plaintext producers keep working during migration. `required` closes that path (HTTP `403`).
- Replace the placeholder `ML_KEM_PSK` in `docker-compose.yml` before using the system anywhere that matters.

Full steps: [Verify the secure channel](../../../README.md#verify-the-secure-channel) and the [ML-KEM integration design](../../security/ml-kem-integration.md).

## 2. Prompts that shaped v2.0.0

### Planning the next work (P001, P002, P003)

After cloning the v1.0.0 prototype, the first prompt asked what to do next. The assistant proposed five work packages (baseline, reliability, ML-KEM, build/deploy, monitoring) and suggested protecting gateway→cloud first. That proposal became the [project plan](../../project-plan.md). P002 produced the README; P003 set up the shared agent rules ([AGENTS.md](../../../AGENTS.md)) and this prompt-record system, recorded in [Decision 0001](../../decisions/0001-shared-agent-instructions.md).

**What we accepted:** the work-package split and the gateway→cloud-first order.\
**What stayed a human decision:** owners, estimates and group acceptance, which were never recorded.

### Testing ML-KEM before it existed (P004)

Prompt: *"can you prepare some test for verifing the ML-KEM(not yet implemented) is it really post-quamtum?"*

**What AI said:** no test can prove an algorithm is post-quantum; that is a property of the underlying Module-LWE problem and of NIST's analysis. Tests can show that the deployment computes the standardised algorithm (NIST ACVP known-answer vectors, FIPS 203 behaviour) and that it is actually used on the protected link.

**What we accepted:** that framing, and the conformance and property suites in `tests/crypto/`. See [ML-KEM verification](../../testing/ml-kem-verification.md).\
**What is unresolved:** the proposed contract in `tests/protected_path/test_protected_path_contract.py` assumes a sessionless design that differs from what was built, so it is still skipped.

### Modularising the device (P005)

The single-file simulator was split into the `device/app/` package with configurable temperature model, range and interval, and a 43-test suite. Evidence: [device modularization validation](../../validation/2026-09-15-device-modularization.md).

### Automated tests and CI/CD (P006)

Parallel sub-agents built per-service unit suites, the Compose integration suite, `scripts/run-unit-tests.sh`, `scripts/smoke-test.sh` and the GitHub Actions workflows. Each service's suite runs from its own directory because all three use a package named `app`. GHCR was chosen as the delivery target because no deployment environment exists. Evidence: [tests and CI/CD validation](../../validation/2026-09-15-tests-and-ci.md).

### Carrying out the plan (P007)

Prompt: *"finish the Suggested next work one by one, please make sure you keep proper documentation of each changes you made."*

One commit per work package. Decisions made by the coordinating session, not the sub-agents:

- ML-KEM runs *inside* the reliability retry loop, so the secure path keeps the same bounded retry and deadline.
- The `cryptography` library's ML-KEM-768 was chosen over the pure-Python `kyber-py` used for test vectors, because `kyber-py` states it is not for cryptographic use. Reasons: [Decision 0002](../../decisions/0002-ml-kem-key-establishment.md).
- Compose ships `enabled`, not `required`, because the device is still a plaintext producer.
- A pre-shared key authenticates the handshake, because ML-KEM alone does not authenticate the peer.
- The plaintext baseline was measured from a clean export of the pre-change commit so the comparison was not contaminated. Measured cost of the secure path: about +1.0% mean end-to-end latency. See the [integration record](../../validation/2026-09-15-integration.md).

### Consolidating and merging (P008)

The parallel sessions' work was consolidated into pull request #1. Its first CI run failed the docs check; the cause was trailing blank lines, but the checker hid its own findings because `git diff --check` exits with code 2. The whitespace was fixed in #1, and the checker defect was fixed with regression tests in #3 on the user's direct instruction.

## 4. Known limitations in v2.0.0

- The device→gateway hop is still plaintext.
- `ML_KEM_PSK` in Compose is a visible placeholder.
- Readings are still stored in memory only and are lost on cloud restart; failed deliveries are not queued.
- The handshake and encrypt/decrypt counters in the crypto packages still read zero, and no Prometheus instance has been run.
- No shared test environment is provisioned.
- One ML-KEM contract test is skipped (see P004 above), and the root `tests/` suites run locally, not in CI.
- Human review of the AI-generated code and group acceptance of the cryptographic library are **not recorded**.

## 5. Evaluating the two versions

The long-lived branches `release/1.0.0` and `release/2.0.0` are kept so each version can be checked out and run side by side:

```bash
git switch release/1.0.0   # v1.0.0 baseline (plus the README and .gitignore edits made on main before v2)
git switch release/2.0.0   # v2.0.0 as released
```

The tags `v1.0.0` and `v2.0.0` mark the exact release commits. `release/1.0.0` points at the last `main` commit before v2.0.0 was merged, which is the `v1.0.0` tag plus two documentation-only changes (the project README and a `local/` ignore entry).
