## 1. S1: nonce reuse and stuck session after a lost response

**Person:** Stanislav Řihák

**Prompt:**
> "v2.3.0 with that scope."
> "ok, you can start now"

**Background:** S1 in [pending-tasks.md](../notes/pending-tasks.md), reproduced at the end of v2.1.0: `SecureCloudClient._send_locked` advanced `session.counter` only after a successful response. When the cloud stored a reading but the response was lost, the next, different reading was encrypted with the same key and nonce (AES-GCM nonce reuse), and the cloud answered `409` to every reading until the session was rekeyed, about 285 s later.

**What AI did:**
- Wrote three regression tests in `tests/crypto/test_gateway_client.py` first: a response lost after the cloud stored the reading; a request lost before it reached the cloud; and a `409` on the gateway's own request.
- Changed `gateway/app/crypto/client.py` so the counter is reserved before the request is sent, and so `409` is handled like `404`/`410` (drop the session, re-handshake, retry the reading once). Updated the comments in `client.py` and `session.py`.
- Updated `docs/security/ml-kem-integration.md`: nonce strategy (a counter is spent when used), failure table (`409` auto-recovered, new row for a lost response), the reasoning for which failures are auto-recovered, and a residual risk for duplicates.

**Decision:** Accepted by Stanley. The change is small and stays inside the gateway client, the cloud and the wire format are unchanged, and the regression tests failed on the old code and pass on the new one, so they show the bug and its fix rather than only passing. The side effect, a possible duplicate reading after a lost response, was accepted knowingly: it matches the plaintext path, is visible in the stored data, and is far less harmful than reusing an AES-GCM nonce or rejecting every reading for about five minutes.

**How it was checked:**
- The three new tests were run against the unchanged client first: all three failed (`409` after the lost response; 3 requests with only 2 distinct nonces; `409` not recovered). After the change they pass.
- Root suites (`tests/crypto tests/reliability tests/protected_path`): `198 passed, 1 skipped` (before the change: `195 passed, 1 skipped`). Gateway suite: `31 passed`. Python 3.14, locally.
- `ruff check .` with the version CI pins (0.14.5): all checks passed. `git diff --check` clean; the two `wire.py` copies are still identical.

**What that check did not prove:**
- The lost response is simulated inside the test transport (the request reaches the in-process cloud, then a `ReadTimeout` is raised). No real network, container or Python 3.12 run.
- The tests call `SecureCloudClient` directly. The path through `send_to_cloud`, which retries timeouts and connection errors, was not tested with the fix.

**Remaining risk:**
- A reading whose response is lost can be stored twice: `send_to_cloud` retries it under the next counter, and the cloud cannot recognise the copy (found by reading `gateway/app/cloud_client.py`, not executed). Before the fix the retry got `409` instead. Detecting duplicates needs a sequence number in the payload (R3 in [pending-tasks.md](../notes/pending-tasks.md)).
- The secure path still ignores the gateway's per-attempt timeout (S5).

## 2. S3, S4: refuse unsafe configuration at startup, and guard the ML-KEM secret length

**Person:** Stanislav Řihák

**Prompt:**
> "no length checks on the ML-KEM -> add it to S3/S4."
> "ok, go ahead with S3/S4"

**Background:** S3 and S4 in [pending-tasks.md](../notes/pending-tasks.md): the committed placeholder `ML_KEM_PSK` was accepted silently, and a mistyped mode (for example `enabeld`) was treated as secure by the gateway while its metric reported `off`, and on the cloud mounted the secure router while every `/secure/*` call returned `403`. The length guard comes from Tom's port of the protected-path tests, which left requirement f unported because `wire.derive_session_key` accepted an empty or short secret.

**What AI did:**
- Added `app/security_config.py`, identical in both services. It rejects any mode other than `off`/`enabled`/`required`. In `required` mode it refuses an `ML_KEM_PSK` that is unset, the placeholder, or shorter than 32 bytes; in `enabled` mode it logs a warning. It sits outside `app.crypto` so the mode is checked without importing the crypto code in `off` mode.
- Wired it into `cloud/app/main.py`, and into the gateway in two places: `cloud_client.py` rejects an unknown mode on import, and `main.py` checks the PSK after logging is configured. Removed the "unknown value counts as off" fallbacks for the metrics, which can no longer be reached.
- Added a length check to `derive_session_key` in both `wire.py` copies: anything other than 32 bytes raises `ValueError`.
- Tests: `tests/crypto/test_security_config.py` (both copies, including a check that they are identical), a length test in `tests/crypto/test_kem_primitives.py`, and `test_*_startup_config.py` in the gateway and cloud suites, which import each service in a fresh interpreter.
- Docs: `docs/security/ml-kem-integration.md` (startup checks, length check, failure table), the README configuration table and PSK note, the Compose comment, and the README's `required` demo, which now generates a real PSK first because the placeholder would stop the cloud.

**Decision:** Accepted by Stanley, with one modification (the warning prefix, below). A typo or a public key now stops a service with a message that names the variable, instead of running in a different mode than the operator asked for, or claiming protection it does not give. Refusing only in `required` mode, and warning in `enabled`, keeps the default Compose setup and CI working. The checks were shown to fail on the old code and were run in containers, and the length guard closes a gap Tom's ported tests had pointed out, with no change to the wire format.

**How it was checked:**
- The code was written before the tests. To make sure the tests detect the problems, they were run against the old production code: the length test failed 10 of 10 cases (5 lengths, 2 copies), and the "refuses to start" tests failed 4 of 4 in each service, while the "starts" cases passed. With the change, everything passes.
- All suites: root `254 passed, 1 skipped` (crypto, reliability, protected_path, tooling); gateway `39 passed`; cloud `31 passed`; device `78 passed`. Python 3.14, locally.
- The cloud was started with `uvicorn`, as in its Dockerfile: `required` with the placeholder PSK exits with code 1 and the message naming `CLOUD_ML_KEM_MODE`; `enabled` with the placeholder starts, answers `/health` with `200` and logs the warning.
- `ruff check .` (0.14.5), `check_docs.py`, `git diff --check` and `docker compose config --quiet` are clean.
- In containers (images built from this branch, Docker 29.4.0, Compose v5.1.2):
  - README `required` demo with `ML_KEM_PSK=$(openssl rand -hex 32)`: plaintext `POST /data` returned `403` and was not stored; readings through the gateway kept arriving (0, then 4 after 16 s); no warnings.
  - Cloud in `required` with the Compose placeholder: container `Exited (1)`, log shows `InsecureConfigurationError: ML_KEM_PSK is the public development placeholder …`.
  - Gateway with `GATEWAY_ML_KEM_MODE=enabeld`: container `Exited (1)`, log shows `GATEWAY_ML_KEM_MODE='enabeld' is not one of off, enabled, required`.
  - Compose defaults (`enabled`, placeholder): both services healthy, readings stored, and both log the placeholder warning.
- That container run showed the gateway printing its warning without the `WARNING:` prefix, because the PSK was checked when `cloud_client` was imported, before `main.py` configured logging. Stanley asked for it to be fixed: the PSK check moved into `main.py` after `logging.basicConfig`. Rebuilt gateway container: `WARNING:app.security_config:ML_KEM_PSK is the public development placeholder …`; gateway suite `39 passed`, root suites `254 passed, 1 skipped`.

**What that check did not prove:**
- The 32-byte minimum counts bytes, not randomness: a long but guessable PSK passes.
- The container runs were local, not on a shared test environment.

**Remaining risk:**
- `enabled` mode still runs with the placeholder, only with a warning. That is what Compose uses by default.- Tom's rewritten `docs/operations/deployment.md` (PR #13, not merged yet) says the placeholder "is accepted without a warning"; it needs updating once both are merged.

## 3. M1–M3: metrics that report what actually happens

**Person:** Stanislav Řihák

**Prompt:**
> "S8 later, remove the three counters."

**Background:** M1–M3 in [pending-tasks.md](../notes/pending-tasks.md). `gateway_cloud_retry_attempts_total` was documented as "retries only" but counted every attempt. `gateway_crypto_encrypt_failures_total`, `gateway_crypto_decrypt_failures_total` and `cloud_crypto_encrypt_failures_total` were never incremented. Rejected `/secure/data` requests other than AEAD failures had no metric. Asked whether to wire or remove the three counters, Stanley asked whether the device → gateway link would be encrypted later (it is not planned: the project keeps the legacy device unchanged and documents that exposure) and why the cloud's reply is plain JSON. That second question showed the reply is not authenticated either: a new finding, S8. Stanley chose to record S8 for later and remove the counters now.

**What AI did:**
- Tests first: two retry-counter tests in `gateway/tests/test_gateway_cloud_client.py`, and `tests/crypto/test_secure_data_metrics.py` (one test per rejection reason, AEAD failures counted only by the decrypt counter, and the three removed counters absent).
- M1: `send_to_cloud` increments the retry counter only from the second attempt on.
- M2: removed the three counters and their wiring notes in both `metrics.py` files. They had no dashboard panels.
- M3: added `cloud_secure_data_rejected_total{reason}` with `malformed`, `unknown_session`, `expired_session`, `replay` and `invalid_payload`, incremented in `cloud/app/crypto/router.py`; added a "Secure Data Rejections by Reason" panel to the dashboard's security row.
- Docs: `docs/operations/monitoring.md` (metric table, alert suggestion), `docs/monitoring/future-features.md`, and S8 in [pending-tasks.md](../notes/pending-tasks.md) and in the residual risks of `docs/security/ml-kem-integration.md`.

**Decision:** Accepted by Stanley. The dashboard now shows what happens instead of numbers that were wrong or could never move: a retry count that matches its definition, no panels that always read zero, and replays and stale sessions visible by reason. The three counters were removed rather than wired because no code path could move them; the one that would become meaningful belongs with S8, which was deliberately left for a later version as a wire-format change. The tests were written first and failed on the old code, and the new counter was seen in `/metrics`, Prometheus and Grafana.

**How it was checked:**
- Against the old code, the new tests failed where expected: the five rejection reasons were not counted (0 instead of 1), the removed counters were still exported, and the retry counter moved by 1 on a first-time success and by 3 instead of 2 when all 3 attempts failed. The AEAD test passed before and after, since that counter already worked.
- After the change: root suites `261 passed, 1 skipped`; gateway `41 passed`; cloud `31 passed`; device `78 passed`; `ruff` clean.
- Stack with the monitoring overlay, built from this branch: two probes to `/secure/data` returned `404` and `400`, `/metrics` showed `cloud_secure_data_rejected_total{reason="unknown_session"} 1.0` and `{reason="malformed"} 1.0`, Prometheus had both targets `up` and stored the series, and the provisioned Grafana dashboard contained the new panel at the end of the security row. `gateway_cloud_retry_attempts_total` was `0.0` with all readings delivered, and the removed counters were absent from `/metrics`.

**What that check did not prove:**
- The panel query returned both reasons with a rate of `0`: the probes ran before Prometheus started scraping, so the graph was not seen rising. The query and panel exist; a live rise was not observed.
- The `replay`, `expired_session` and `invalid_payload` reasons were checked in-process only, not against the running stack.

**Remaining risk:**
- A `422` from FastAPI's own request validation (missing or wrongly typed fields) is rejected before the handler runs, so `cloud_secure_data_rejected_total` does not count it.
- S8 is open: a forged `200` reply is invisible to every metric.

## 4. M4, M5: alert rules and Compose healthchecks

**Person:** Stanislav Řihák

**Prompt:**
> "I accept, draft the reasoning and continue with M4/M5"

**Background:** M4 and M5 in [pending-tasks.md](../notes/pending-tasks.md). The course brief asks for outage detection, but Prometheus had no rules: `docs/operations/monitoring.md` only suggested some. Compose had no healthchecks, so the gateway and device could start before the service they depend on.

**What AI did:**
- `monitoring/alerts.yml`: eight rules in three groups. Availability: `ServiceDown`, `NoReadingsStored`. Delivery: `DeliveryFailuresHigh`, `DeliveryFailuresCritical` (thresholds from the earlier suggestions). ML-KEM: `HandshakesFailing`, `HandshakeAuthenticationFailures`, `AeadDecryptFailures`, `SecureDataReplays` (the last uses the M3 counter). Loaded through `rule_files` in `monitoring/prometheus.yml` and mounted by the overlay.
- `monitoring/alerts.test.yml`: `promtool` unit tests. A healthy system fires nothing; each failure case fires its alert with the expected labels and text.
- `docker-compose.yml`: healthchecks on the cloud and gateway calling `/health` with Python's `urllib` (the images have no `curl`). The gateway waits for a healthy cloud, the device for a healthy gateway.
- Docs: an "Alert rules" section in `docs/operations/monitoring.md` (the old suggestions remain as "Further alert ideas"), `docs/monitoring/future-features.md`, `monitoring/README.md`, the README's known limitations, and the header comment of `scripts/smoke-test.sh`. The README change also removes two statements that were no longer true ("no Prometheus instance has been run", "the handshake and encrypt/decrypt counters … still read zero"; D3 in pending-tasks).

**Decision:** Accepted by Stanley. The project now detects an outage instead of only displaying one: a stopped cloud raised a firing alert within 80 seconds and cleared on recovery, which covers the brief's outage-detection requirement. The rules are tested like code, and the tests were shown to catch wrong thresholds, so later changes to the rules can be checked. The healthchecks remove the start-up race without changing any service. Sending alerts to people (Alertmanager) and running the rule tests in CI were left out on purpose: the first is beyond a local course deployment, and the second touches the CI file of Tom's open PR.

**How it was checked:**
- `promtool check rules`: `SUCCESS: 8 rules found`; `promtool check config` loads the rules through `prometheus.yml`; `promtool test rules`: `SUCCESS`.
- To make sure the unit tests can fail, they were run against a copy of the rules with three deliberate mistakes (`for: 5m` instead of `1m`, `0.6` instead of `0.2`, `malformed` instead of `replay`): the tests failed for `ServiceDown`, `DeliveryFailuresCritical` and `SecureDataReplays`.
- Full stack with the overlay, built from this branch: Compose started the cloud, waited for `Healthy`, then the gateway, waited for `Healthy`, then the device. Prometheus loaded 8 rules and showed no alerts while healthy. After `docker compose stop cloud`, `ServiceDown{job="cloud"}` was pending at +20 s and firing at +80 s; both delivery alerts went pending at +40 s; the gateway answered a reading with `502`. After `docker compose start cloud`, `ServiceDown` cleared within 10 s, the cloud was `healthy` again and readings were stored again.
- `scripts/smoke-test.sh` (the CI smoke test) passed locally: both containers reported `Healthy`, integration suite `7 passed`.
- `docker compose config --quiet` (with and without the overlay), `check_docs.py`, `git diff --check` and `ruff` are clean.

**What that check did not prove:**
- The delivery alerts were not watched until they fired (their window is 5 + 5 minutes), and `NoReadingsStored` and `HandshakesFailing` were checked only in the unit tests, not live.
- The thresholds are sized for one device sending every 5 seconds; they were not tried with other traffic.
- CI does not run the `promtool` tests. Adding a job means changing `.github/workflows/ci.yml`, which Tom's open PR #13 also changes.

**Remaining risk:**
- Alerts are not delivered: no Alertmanager, so someone has to open http://localhost:9090/alerts.
- After a short outage the delivery alerts can still fire a few minutes after recovery, because the failures stay in their 5-minute rate window (reasoned from the rule definitions; observed only as far as "still pending 90 s after recovery").
- The healthchecks are liveness only: a gateway whose cloud is down stays `healthy`.
- Running `scripts/smoke-test.sh` locally ends with `docker compose down -v`, which also deletes the `cloud-keys` volume, so the cloud generates a new ML-KEM key pair on its next start. That breaks a pinned fingerprint if one is set; it is the script's existing behaviour, not a change here.

## 5. S7: security evidence against the running system

**Person:** Stanislav Řihák

**Prompt:**
> "I accept, draft the reasoning and continue with S7"

**Background:** S7 in [pending-tasks.md](../notes/pending-tasks.md): the report needs expected-vs-actual evidence for wrong PSK, tampering, replay, expired session, forbidden plaintext in `required` mode and the S1 scenario, including whether anything was wrongly stored, plus handshake and message latency for new and reused sessions. The in-process tests cover these cases, but not against the containers.

**What AI did:**
- `scripts/evaluation/security_evidence.py`: runs nine cases over real HTTP against the cloud, using the real gateway client with faults injected in its transport, and records the status, readings stored for that case, and the change in the relevant cloud metric. It then times reused-session requests, new-session requests and handshakes (200 samples each). It exits with 1 if any case differs from its expectation. The forged-reply case is marked as a known gap (S8) rather than a pass.
- [`docs/validation/2026-09-29-security-evidence.md`](../../validation/2026-09-29-security-evidence.md): method, environment, both result tables and limits; linked from `docs/README.md`.

**Decision:** Accepted by Stanley. The report needs evidence from the running system, not only from unit tests, and this gives it for every case S7 listed, including the check that nothing was wrongly stored. The script is repeatable, so the table can be regenerated for the final evaluation, and it was shown to fail on the code from before the S1 fix, which makes it a before-and-after comparison rather than a list of passes. The S8 result is reported as an open weakness instead of being left out.

**How it was checked:**
- Run against the stack at `e40e325` (cloud in `required` mode, random 64-character PSK, 20-second session TTL via a temporary override): all eight protection cases as expected, nothing wrongly stored, each rejection moved its metric by exactly 1; S8 confirmed (client reported stored, 0 readings stored). Latency medians: reused session 3.51 ms, new session 10.75 ms, handshake 7.14 ms; p95 6.12 / 14.82 / 10.44 ms.
- To show the script can detect a failure, it was run with the gateway client from before the S1 fix (`0f309bd`, in a temporary worktree) against the same containers: the S1 case reported `409, nonce reused` with 2 of 3 readings stored, and the script exited with 1.
- `ruff` clean on the script; `check_docs.py` and `git diff --check` clean.

**What that check did not prove:**
- One local host with loopback networking: no real network delay or loss, and the latency numbers include Docker's port mapping.
- The client ran on the host (Python 3.14), not in the gateway container.
- A machine-in-the-middle answering the handshake, a pinned-fingerprint mismatch and handshake flooding were not part of this run; the first two are covered only by in-process tests.

**Remaining risk:**
- S8 is open and invisible to monitoring.
- The script is not part of CI; it needs a running stack in a specific configuration.
