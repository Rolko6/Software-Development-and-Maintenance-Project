## P012: A realistic legacy device, and the NaN defect it exposes

- Person: Rolko6
- Recorded: 2026-09-28, from the same session; prompts given on 2026-09-26; not contemporaneous.
- Assistant / model: Claude Code, Opus 5.5.
- Context and revision: `feat/ds18b20-device` at `9bb782a`. Files read: `device/app/*.py`, `device/tests/test_sensor.py`, `gateway/app/models.py`, `gateway/app/metrics.py`, `gateway/requirements.txt`.

### Prompt

[I was thinking that a proper legacy device should be something like an Arduino sensor, something that simulates reality better and has more problems that need testing. I don't know whether Python has libraries that can simulate something like that better. What do you think?]

Follow-ups:

[I'd go with the first approach, the DS18B20, I just want you to explain it more: a plan of what to do, what would happen and how it changes the system.]

[So if I understand correctly, when the device sends NaN the gateway must be able to handle it correctly. I want to understand the realistic scenario of the system once I implement the new device, so that it works, and how to test it and see it realistically.]

### Output and disposition

- The assistant proposed three options: (A) a realistic DS18B20 model with configurable fault injection in pure Python, (B) network faults injected from outside with Toxiproxy or Pumba, (C) real Arduino firmware in an emulator such as Wokwi, or MicroPython. It recommended A, possibly later combined with B, and advised against C as far more complex for little gain. It said it had not tried the tools in B and C in this project. **Human decision: the user chose A, the DS18B20 model.**
- To predict what the gateway would do with each fault, the assistant ran the gateway's `SensorData` model under FastAPI 0.115.6 in a scratch environment outside the repository. That showed `-127.0` and `85.0` returning `422`, but `NaN` returning **500**: validation rejects it, then the `422` body echoing the rejected `nan` cannot be serialised. It also showed that `requests` refuses to encode `NaN` at all (`InvalidJSONError`, a `RequestException`). This corrected an earlier statement in the same conversation that Python would send `NaN` as invalid JSON.
- Reading `gateway/app/main.py` against `gateway/app/metrics.py` showed that `rejected_validation` is documented but never incremented for a reading that fails gateway validation.
- These findings were a proposal and an isolated reproduction; they were confirmed on the running stack and fixed on 2026-09-28 ([P013](2026-09-28-Rolko6.md#p013-simulate-a-faulty-ds18b20-and-fix-what-it-exposes)).

### Verification and remaining uncertainty

- Executed: the scratch reproduction above, which gave `NaN -> 500`, `85.0 -> 422`, `-127.0 -> 422` and `22.06 -> 200`. It exercised the gateway model in a minimal app, not the running gateway.
- The DS18B20 facts used (0.0625 °C at 12-bit resolution, ±0.5 °C accuracy, `-127` from the DallasTemperature library for a missing sensor, `85` as the power-on reset value) are from the assistant's general knowledge; no datasheet was consulted or recorded.
