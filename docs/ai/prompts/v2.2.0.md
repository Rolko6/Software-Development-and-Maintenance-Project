## Behaviour changes

Nothing changes unless it is asked for: the default device is still the fault-free `uniform` model, and every `FAULT_*` rate defaults to 0.

| Area | v2.1.0 | v2.2.0 |
| --- | --- | --- |
| `NaN` or `Infinity` temperature sent to the gateway or to the cloud's `POST /data` | `500 Internal Server Error` and a traceback | `422`; the rejected input is echoed as the string `"nan"` or `"inf"` |
| A reading that fails gateway validation | `422`, no metric, no `device_id` in the log | `422`, `gateway_delivery_outcome_total{outcome="rejected_validation"}` incremented, `WARNING` with the `device_id` |
| Device producing a `NaN` reading | Not possible | Sent as a raw JSON body; the gateway's `422` is logged as a rejected reading, not as a network failure |

The `422` body is unchanged for every finite input. A client that treated a `500` on a `NaN` reading as a retryable server error now receives a `4xx`, which should not be retried.

## Known limitations

- Validation checks the range only: a stuck or slowly drifting sensor is stored as valid.
- Rejected readings are counted but not timed in `gateway_request_duration_seconds`.
- Open: occasional `RemoteDisconnected` on valid readings, suspected to be the gateway's 5-second keep-alive meeting the device's 5-second interval, not reproduced; and a live rejection share above the model's expectation. Both are described in the validation record.
- The v2.1.0 [pending tasks](../notes/pending-tasks.md) still apply; this version does not address them.
