## 1. Understanding the assignment

**Prompt:**
> "Explain to me what the teacher wants us to do, but do it in a way that is easy to understand, you can also provide practical examples of how you would implement it. My main problem is even though I have read it I still don't know how to do it or how to start."
> *(SDMO_Project.pdf attached)*

**What AI summarized:**
- Phase 1: Get the existing system running. Understand what each component does before changing anything.
- Phase 2: Find the weak parts — gaps in testing, CI/CD, monitoring, and security (specifically the legacy key exchange).
- Phase 3: Improve, document, and deliver.
- Key rule: use an LLM to help, but treat its output as unverified. Evaluate generated code for correctness, security, and maintainability. Document every significant prompt, what was accepted, what was changed, and why.

**What we accepted:** The 3-phase framing. It directly shaped how we approached the project — baseline first, ML-KEM second.

**What we accepted:** The 3-service split (device / gateway / cloud), the per-service Dockerfile structure, and the code for the core files (`device.py`, `gateway/app/main.py`, `cloud/app/main.py`, `cloud/app/storage.py`, `gateway/app/metrics.py`, `gateway/app/cloud_client.py`, `docker-compose.yml`). This became v1.0.0.

**What we rejected / deferred:**
- ML-KEM client/server code — AI included gateway encryption and cloud decryption in the same step. We explicitly deferred this to v2.0.0 to keep the baseline simple and verifiable.
- Root-level `tests/` folder — per-service test organisation was used instead when tests were added in v2.0.0.
- The `docs/` structure AI suggested differed from what was actually adopted.

**Why we deferred ML-KEM:** The AI proposed jumping directly to encryption in the first version. We decided a clean, working unencrypted baseline is more valuable as a starting point — it gives a known-good reference to compare against after encryption is added.

**Verification:** `docker compose up --build` starts all three services. Gateway `/health` returns 200. Cloud `/data` stores and returns readings.

## 3. GitHub releases and versioning strategy

**Prompt:**
> "In this project, we would like to implement releases like other projects have on GitHub. My thinking is we want to divide the project into phases — this first phase which you provided code for is the first phase, so for example v1.0.0. If we later implement a better device, that will be another phase. Does that make sense? Can we do that with GitHub releases? That way we can write a separate README for each phase and explain what that phase does. Tell me if that is a good approach or if there is a better one. Create content for the README file for phase 1 of the project."

**What AI recommended:** Yes — use Git tags and GitHub Releases to mark completed phases. However, don't create separate README files in the root for each phase (README-v1.0.0.md, README-v1.1.0.md, ...) — that becomes messy. Instead:

```
README.md                  ← describes the project as a whole
docs/phases/
├── v1.0.0.md
├── v1.1.0.md
├── v1.2.0.md
├── v2.0.0.md
└── ...
```

The root README links to each phase doc. GitHub Releases provide the historical snapshots.

AI also proposed a version table inside the README:

| Version | Milestone |
| --- | --- |
| v1.0.0 | Initial Edge-Cloud Baseline |
| v1.1.0 | Testing & Quality Improvements |
| v1.2.0 | Monitoring & Operational Improvements |
| v2.0.0 | ML-KEM Integration |
| v2.1.0 | Legacy Migration & Compatibility |
| v3.0.0 | CI/CD & Test Deployment |

**What we accepted:** The Git tag approach and the idea of per-phase documentation files. The actual folder we used (`docs/ai/prompts/`) differs from `docs/phases/` but follows the same principle.

**What we simplified:** The 6-version roadmap was collapsed into 2 major releases (`v1.0.0` and `v2.0.0`). The intermediate milestones (testing, monitoring, CI/CD) were all incorporated into v2.0.0 rather than released separately.
