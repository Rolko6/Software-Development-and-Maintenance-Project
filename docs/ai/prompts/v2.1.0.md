## P001 — Implement crypto metrics for gateway and cloud

**Prompt (paraphrased):** Implement metrics for both modules (gateway and cloud) so
that they actually work and Prometheus can scrape data from the handshake and secure
data paths.

**Context:** The metrics counters and histograms were already defined in
`gateway/app/metrics.py` and `cloud/app/metrics.py` as part of v2.0.0, but no
`.inc()` or `.observe()` calls were ever wired into the actual crypto code. All
crypto-related counters therefore read zero regardless of how many handshakes or
encrypted messages were processed.

**What was changed:**

`gateway/app/crypto/client.py`:
- Added imports of `GATEWAY_HANDSHAKE_STARTED_TOTAL`, `GATEWAY_HANDSHAKE_SUCCEEDED_TOTAL`,
  `GATEWAY_HANDSHAKE_FAILED_TOTAL`, `GATEWAY_HANDSHAKE_DURATION_SECONDS`, and
  `GATEWAY_SESSION_REKEYS_TOTAL` from `..metrics`.
- Added `_classify_handshake_error(exc)` helper that maps exception types to the fixed
  reason labels (`timeout`, `peer_unavailable`, `decode_error`, `verification_failed`,
  `other`).
- Wrapped `_handshake()` in a try/except: increments `STARTED` on entry, `SUCCEEDED`
  and duration (outcome=`success`) on the happy path, `FAILED` with the classified
  reason and duration (outcome=`failure`) on any exception.
- Modified `_ensure_fresh_session()` to increment `GATEWAY_SESSION_REKEYS_TOTAL`
  (reason=`expired`) when an existing session is proactively replaced because it is
  near its TTL.
- Modified `_send_locked()` to increment `GATEWAY_SESSION_REKEYS_TOTAL`
  (reason=`forced`) when the cloud returns 404/410, meaning the session was unknown
  or expired on the cloud side and a reactive re-handshake is triggered.

`cloud/app/crypto/router.py`:
- Added `import time`.
- Added imports of `CLOUD_HANDSHAKE_STARTED_TOTAL`, `CLOUD_HANDSHAKE_SUCCEEDED_TOTAL`,
  `CLOUD_HANDSHAKE_FAILED_TOTAL`, `CLOUD_HANDSHAKE_DURATION_SECONDS`, and
  `CLOUD_CRYPTO_DECRYPT_FAILURES_TOTAL` from `..metrics`.
- Instrumented `do_handshake()`: increments `STARTED` on entry; at each failure path
  increments `FAILED` with the appropriate reason label (`other`, `decode_error`, or
  `verification_failed`) and records the duration with outcome=`failure`; increments
  `SUCCEEDED` and records duration with outcome=`success` just before the return.
- Added `CLOUD_CRYPTO_DECRYPT_FAILURES_TOTAL.inc()` inside the `except InvalidTag`
  block in `receive_secure_data()`.

**Verification:** Not yet run — requires a live Docker Compose stack with the
monitoring stack (`monitoring/docker-compose.monitoring.yml`) and a Prometheus scrape
to confirm the counters move.

## P002 — Enforce that the two copies of wire.py stay identical

**Prompt:** "One file is just copied so there are 2 identical files for monitoring right?"

**Context:** `cloud/app/crypto/wire.py` and `gateway/app/crypto/wire.py` are
intentionally identical copies of the shared wire-format and crypto helpers. Because
the two services build into separate Docker images they cannot import from each other,
so the file is duplicated. The risk is that someone edits one copy and not the other,
causing the gateway and cloud to silently disagree on the protocol. Nothing in CI
previously caught this.

**What was changed:**

`.github/workflows/ci.yml`:
- Added a step in the `lint` job that runs `diff cloud/app/crypto/wire.py
  gateway/app/crypto/wire.py`. If the files differ, the step prints a clear error
  message and fails CI, blocking the pull request until both copies are brought back
  into sync.

**Verification:** The diff step exits 0 (no difference) on the current state of the
repository, confirming the two files are still identical.

## P003 — Grafana dashboard

**Prompt:** "I want you to make a Grafana dashboard. Pick metrics that are meaningful
for our project and worthwhile showing."

**What was changed:**

Two new files created under `monitoring/grafana/provisioning/dashboards/`:

`dashboard.yml` — Grafana provisioning config that tells Grafana to load all JSON
files from `/etc/grafana/provisioning/dashboards/` at startup. Without this file
Grafana does not know to look for dashboard JSON files in that directory.

`project.json` — The dashboard itself. 17 panels across 5 rows:

- **Row 1 — Health at a glance (stat panels):** total readings received, total
  forward failures (red if > 0), current readings in memory, total storage evictions.
  Gives an instant system health summary without reading any graphs.

- **Row 2 — Throughput (line graphs):** per-second reading rate arriving at the
  gateway; delivery outcome breakdown split by label (forwarded / rejected /
  failed\_after\_retries) on one chart. Shows whether data is flowing and whether
  failures are spiking.

- **Row 3 — ML-KEM handshakes (line graphs):** handshake rate started vs succeeded
  on one chart (a persistent gap = failures); handshake duration p50 and p95.
  Shows how often the gateway re-keys and how long it takes.

- **Row 4 — Security alarms (line graphs, should stay flat at zero):** AEAD decrypt
  failures (any rise = tampering or session bug), handshake auth failures filtered
  by reason=`verification_failed` (wrong PSK or MITM attempt), forced and proactive
  session rekey rates. These panels have red thresholds so they stand out if anything
  goes wrong.

- **Row 5 — Latency comparison (line graphs):** gateway request duration p50 and p95
  each split by `security_mode` label. Directly shows the overhead ML-KEM adds over
  plaintext — the core measurement question for the course project.

The Grafana datasource (`Prometheus`, provisioned in `datasources/prometheus.yml`) is
referenced by name in every panel target so the dashboard works without any manual
configuration. The dashboard auto-refreshes every 15 seconds and defaults to a 30-
minute time window.

**Verification:** Not yet run — requires starting the monitoring stack with
`docker compose -f docker-compose.yml -f monitoring/docker-compose.monitoring.yml up --build -d`
and opening `http://localhost:3000` to confirm the dashboard loads and panels populate.
