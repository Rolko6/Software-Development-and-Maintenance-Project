## 1. Implement crypto metrics for gateway and cloud

**Person:** Stanislav Řihák

**Prompt:**
> "Implement metrics for both modules (gateway and cloud) so that they actually work and Prometheus can scrape data."

**Background:** `gateway/app/metrics.py` and `cloud/app/metrics.py` already declared all the counters and histograms in v2.0.0, but no `.inc()` or `.observe()` calls existed anywhere in the crypto code. Every metric read zero regardless of how many handshakes or encrypted messages the system processed.

**What AI did:**
- Added a `_classify_handshake_error()` helper to the gateway crypto client that maps exception types to reason labels (`timeout`, `peer_unavailable`, `decode_error`, `verification_failed`, `other`).
- Wrapped `_handshake()` with STARTED / SUCCEEDED / FAILED counters and a duration histogram. Added rekey counter increments for proactive TTL expiry (reason `expired`) and forced rekeys triggered by 404/410 responses from the cloud (reason `forced`).
- Instrumented `do_handshake()` and `receive_secure_data()` in the cloud crypto router with the same started / succeeded / failed pattern plus a decrypt-failure counter on AEAD tag mismatch.

**Decision:** Accepted. The instrumentation follows the label sets already defined in `metrics.py`, so no new series were introduced.

**How it was checked:** the monitoring stack was brought up, and Prometheus showed non-zero counter values after readings were sent through the system.

**What that check did not prove:** a non-zero counter shows that the code runs, not that it counts the right thing. A later source review against the definitions in `metrics.py` found:
- `gateway_cloud_retry_attempts_total` is defined as "retries only, excluding the first attempt", but `send_to_cloud` increments it before every attempt, including the first. This was already the case in v2.0.0; the v2.1.0 check did not catch it.
- `gateway_crypto_encrypt_failures_total`, `gateway_crypto_decrypt_failures_total` and `cloud_crypto_encrypt_failures_total` are still never incremented. The gateway never decrypts a cloud response, so its decrypt counter cannot move.
- On the cloud, only AEAD tag failures on `/secure/data` are counted. Unknown or expired sessions (404/410), replayed counters (409) and invalid decrypted payloads (400) have no metric, so a replay attempt is invisible on the dashboard.

**Remaining risk:** until these are fixed, the retry panel overstates retries and a replay attack does not show on any panel. Tracked as M1–M3 in [pending tasks](../notes/pending-tasks.md).

## 2. Enforce that the two copies of wire.py stay identical

**Person:** Stanislav Řihák

**Prompt:**
> "One file is just copied so there are 2 identical files for monitoring right?"

**Background:** `cloud/app/crypto/wire.py` and `gateway/app/crypto/wire.py` are intentionally identical copies of the shared wire-format and crypto helpers. Because the two services run in separate Docker images they cannot import from each other. The risk is a developer edits one copy and not the other, silently breaking the protocol. Nothing in CI previously caught this.

**What AI did:** Added a step to the `lint` job in `.github/workflows/ci.yml` that runs `diff cloud/app/crypto/wire.py gateway/app/crypto/wire.py`. If the files differ, CI fails with a clear error message before any code is built or tested.

**Decision:** Accepted. The alternative, a shared package installed into both images, removes the duplication but changes both Dockerfiles and the test import setup; a one-line check gives the same protection for much less change.

**How it was checked:** `diff` exits 0 on the current repository, and the Lint job passed on PR #7.

**What that check did not prove:** it only shows the copies are identical, not that they are correct. A bug in `wire.py` would be copied faithfully into both services.

**Remaining risk:** the check was not tested with a deliberately edited copy, so a failing run has not been observed.

## 3. Grafana dashboard

**Person:** Stanislav Řihák

**Prompt:**
> "I want you to make a Grafana dashboard. Pick metrics that are meaningful for our project and worthwhile showing."

**What AI created:** Two files under `monitoring/grafana/provisioning/dashboards/`:

- `dashboard.yml` — tells Grafana to auto-load JSON files from the provisioning directory at startup.
- `project.json` — 17 panels across 5 rows:
  - **Health at a glance** — stat panels for total readings received, total forward failures, readings in memory, and total storage evictions. Colour thresholds turn red if failures exceed 0.
  - **Throughput** — reading rate per second; delivery outcome split (forwarded / rejected / failed after retries).
  - **ML-KEM handshakes** — started vs succeeded rate (a persistent gap means failures); handshake duration p50 and p95.
  - **Security alarms** — AEAD decrypt failures, handshake auth failures, forced and proactive session rekeys. These panels have red thresholds and should stay flat at zero in normal operation.
  - **Latency comparison** — gateway request duration p50 and p95 split by `security_mode`, to measure the overhead ML-KEM adds over plaintext.

**Problem found and fixed:** when the dashboard was run locally, the panels could not connect to Prometheus. The dashboard refers to its datasource as `uid: prometheus`, but `monitoring/grafana/provisioning/datasources/prometheus.yml` did not set a UID, so Grafana assigned a random one at startup. `uid: prometheus` was added to the datasource file. CI does not start the monitoring stack, so only a local run could have exposed this.

**Decision:** Accepted with that fix.

**How it was checked:** after the fix and a Grafana restart, the dashboard loaded at `http://localhost:3000` and all panels displayed live data.

**What that check did not prove:** "live data" was seen in normal operation only. The security-alarm panels are meant to stay at zero, so seeing zero does not show that they react to an attack; no tampering, replay or wrong-PSK run has been made against the dashboard. The handshake duration panels do not aggregate across the `outcome` label, so successful and failed handshakes appear as separate series. The latency comparison needs runs in both `off` and `enabled` modes (noted in `docs/monitoring/future-features.md`).

**Remaining risk:** a panel can look healthy because the event it watches never happens or is never counted (see entry 1). Dashboards show state but do not alert; Prometheus has no alert rules yet (M4 in [pending tasks](../notes/pending-tasks.md)).

## 4. Add root-level test suites to CI

**Person:** Stanislav Řihák

**Prompt:**
> "yes" *(confirming: add a CI job for `tests/crypto/`, `tests/reliability/`, and `tests/protected_path/`)*

**Background:** These three suites verify ML-KEM handshake conformance, session replay defence, reliability behaviour, and the protected-path contract. They were not in CI because: the smoke job hard-codes `tests/integration/`; the crypto suite uses a `kyber-py` private API that requires careful version pinning; and both gateway and cloud packages are named `app`, requiring an `importlib` alias trick to load them together in one Python process without collision. The root `requirements-dev.txt` and `pytest.ini` already handled all of this — the only missing piece was a CI job.

**What AI did:** Added a `test-root` job to `.github/workflows/ci.yml`. The job checks that the three test directories and `requirements-dev.txt` exist, installs dependencies, runs `pytest`, uploads a JUnit report as an artifact, and writes a pass/fail summary to the GitHub job summary page. Added `test-root` to the `smoke` job's `needs` list so the smoke test only runs after both per-service and root-level suites pass.

**Decision:** Accepted, then corrected in entry 5.

**How it was checked:** the job was run by CI on the pull request, where it **failed**. The AI's "the only missing piece was a CI job" was wrong: the root `requirements-dev.txt` did not contain the service dependencies the suites import.

**What this shows:** the job had never been run before it was accepted. Running it in CI is what exposed the missing dependencies, which is why entry 5 exists.

## 5. Fix missing dependencies in root requirements-dev.txt

**Person:** Stanislav Řihák

**Prompt:**
> CI error on the pull request: `ModuleNotFoundError: No module named 'cryptography'` when running the `test-root` job.

**Background:** The `test-root` CI job installs only the root `requirements-dev.txt` before running `tests/crypto/`, `tests/reliability/`, and `tests/protected_path/`. Those suites load the gateway and cloud app packages in-process, which import `cryptography` and `fastapi` at module level. Both packages were pinned in each service's own `requirements.txt` but were never added to the root file. Pytest therefore failed at collection with an `ImportError`, and the JUnit artifact upload failed as a second consequence because no report file was written.

**What AI did:** Added `cryptography==50.0.1` and `fastapi==0.115.6` to `requirements-dev.txt` with a comment explaining why they are needed there alongside the test-only dependencies.

**Decision:** Accepted. The versions match the pins in the service `requirements.txt` files, so the tests run against the same library versions as the containers.

**How it was checked:** all eleven CI checks passed on [PR #7](https://github.com/Rolko6/Software-Development-and-Maintenance-Project/pull/7), including "Root-level tests (crypto / reliability / protected-path)".

**Remaining risk:** the pins now exist in three files and can drift apart. CI runs Python 3.12 like the containers, but local runs may use a newer Python.

## Known limitations

- The metrics problems found in entry 1 (retry counter, failure counters that never change, secure-data rejections not counted) are not fixed in this version.
- Prometheus has no alert rules; the dashboard shows state but does not alert.
- The end-of-version review also found an open security defect in the ML-KEM client: after a lost response the gateway can reuse an AES-GCM nonce, and the session then rejects readings until it is rekeyed. See S1 in [pending tasks](../notes/pending-tasks.md).
- Everything listed under "Known limitations" in [v2.0.0.md](v2.0.0.md) that this version did not address still applies, except the crypto handshake counters, which are now wired.
