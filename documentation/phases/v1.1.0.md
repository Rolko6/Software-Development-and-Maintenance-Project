## 1. Overview

v1.1.0 adds automated tests for the v1.0.0 baseline — no production code changed. Tests lock in current behavior (including known gaps) so future versions have a regression safety net before ML-KEM and other changes land.

---

## 2. AI-Assisted Development

### Test approach

**Prompt:** "Suggest an approach for how you would create unit/API tests for the device, gateway, and cloud."

**Output:** pytest + FastAPI `TestClient` (gateway/cloud) + `unittest.mock` to mock outbound `requests.post` calls (no real network between services needed). One `tests/` folder per service, each with a `conftest.py` that adds the service root to `sys.path`.

**Decision:** Accepted as-is.

---

### Cover DS18B20 sensor-error behavior ahead of v1.3.0

**Prompt:** "It's important to make these tests cover the behavior of the legacy device, which will later become a DS18B20."

**Output:** gateway/cloud don't care who sent the data, so added 3 gateway tests using real DS18B20 error-sentinel values (85.0 = power-on-reset, -127.0 = CRC failure, 500.0 = out of physical range). They currently pass because there's no range validation — intentional, documents today's gap for v1.3.0 to revisit.

**Decision:** Accepted, added to `gateway/tests/test_gateway_main.py`.

---

### When to write tests: before or after the code?

**Prompt:** "Isn't the correct way to first write tests before implementation, and only then the implementation?"

**Output:** depends on context — for already-existing code (this baseline), tests written after are "characterization tests" (standard for legacy code, and what the assignment's phase order implies). For new functionality not yet built (ML-KEM), test-first/TDD is the better fit, since it forces defining the expected contract before implementing.

**Decision:** Keep test-after for this baseline (v1.1.0). Use test-first for ML-KEM in v2.0.0.

## 3. Baseline Analysis

**How to run tests** (each service separately — see Section 4 for why):
```powershell
python -m pytest gateway/tests
python -m pytest cloud/tests
python -m pytest device/tests
```
Dependencies in `requirements-dev.txt` (root).

**Test results (executed 2026-10-04):** 16/16 passing.
- gateway: 8 tests — health, valid forward, 422 validation (empty `device_id`, missing `temperature`), 502 on cloud failure, 3 DS18B20 boundary values
- cloud: 5 tests — health, store+retrieve round trip, storage unit tests, confirms cloud accepts empty `device_id` (looser validation than gateway)
- device: 3 tests — generated data shape/range, successful send, `RequestException` handled without crashing

## 4. Critical Evaluation & Maintenance

### Running all three services' tests together silently breaks
- **How discovered:** running `pytest gateway/tests cloud/tests device/tests` in one command
- **Problem:** gateway and cloud both have a top-level package named `app`. In one pytest process, the second service's `app` import gets shadowed by the first's (Python caches modules by name), causing unrelated test failures.
- **Fix:** run each service's tests in its own `pytest` process. Noted for v1.2.0 — the CI pipeline needs a separate job/step per service, not one combined test run.

### Test file name collision
- **How discovered:** same run as above — pytest's "rootless" import mode doesn't allow two `test_main.py` files with no `__init__.py` in the same session.
- **Problem:** `gateway/tests/test_main.py` and `cloud/tests/test_main.py` collided.
- **Fix:** renamed to `test_gateway_main.py` and `test_cloud_main.py`.

## 7. Final Evaluation

- **Strengths:** 16 passing tests covering the full baseline including edge cases; known gaps (validation, sensor sentinels) are now explicit, documented tests instead of just prose.
- **Weaknesses:** tests only run manually; nothing stops someone from breaking the baseline without noticing.
- **Technical debt:** the `conftest.py` `sys.path` trick is a workaround, not a proper package setup — fine for now, but something a packaging cleanup could remove later.
- **Risks:** the `app` package name collision (Section 4) must be accounted for when designing the v1.2.0 CI pipeline, or it will silently produce wrong results.
