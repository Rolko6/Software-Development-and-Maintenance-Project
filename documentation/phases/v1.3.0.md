# Documentation — v1.3.0 (Realistic Device Simulation — DS18B20)

**Date:** October 4, 2026
**Author(s):** Roland Budzák
**Tool:** Claude (Claude Code)
**Scope of this version:** Replace the device's pure-random temperature generator with a realistic DS18B20 simulation — smooth drift, error sentinels, a stuck/frozen sensor, and intermittent disconnects.

---

## 1. Overview

v1.0.0's `device.py` generated a brand new random temperature every cycle, which no real sensor does. v1.3.0 replaces that with a model closer to how a real DS18B20 actually fails: gradual drift under normal conditions, occasional nonsense readings, a sensor that freezes on the same value for a while, and a sensor that doesn't respond at all. Only `device/device.py` changed — gateway and cloud are untouched.

---

## 2. AI-Assisted Development

### Who should handle bad readings — device or gateway?

**Prompt:** "In a real scenario, does the device know how to detect a sensor failure, or should it send it through the gateway and let the gateway handle it — which is more realistic but also simple for us, since this is just a simulation? And how do I test this with different percentages of faulty data — how much is erroneous, how much is sensor failure, maybe when the sensor gets stuck, etc."

**Output:** Split into two distinct cases. A sensor that *responds* but with a nonsense value (85.0, -127.0) isn't something a dumb/legacy device can interpret — it has no domain logic, so it just forwards it, and the gateway (the modernized layer) is the one that should eventually decide what to do with it. A sensor that *doesn't respond at all* is a communication-level failure the device genuinely can detect on its own — nothing to send that cycle. Also proposed a third fault mode (frozen/stuck sensor, repeating the same value for several reads) and a testing strategy: deterministic tests that force each branch via mocking/monkeypatching, instead of relying on true randomness.

**Decision:** Accepted. Device forwards error sentinels unchanged (gateway's job to validate — already tracked as an open gap, see v1.0.0 Section 4); device only skips sending on a genuine disconnect; added the stuck-sensor fault mode.

---

### Implementation

**Prompt:** "ano sedi to podme na to" (confirmation to implement the design above).

**Output:** `read_sensor()` rolls once per read against three independent rates (`DISCONNECT_RATE`, `ERROR_RATE`, `STUCK_START_RATE`, all env-configurable) to pick one of: disconnected (`None`) / error sentinel / start of a stuck episode (3-8 repeated reads) / normal reading (random walk, ±0.3°C per step, clamped to 15-30°C). `generate_sensor_data()` returns `None` on disconnect; `send_data()` skips sending (and logs it) when that happens.

**Decision:** Accepted as implemented, then verified (Section 3).

## 3. Baseline Analysis

**How to run:** same as before (`docker compose up --build -d`), or locally:
```powershell
$env:ERROR_RATE = "0.3"; $env:DISCONNECT_RATE = "0.3"; $env:STUCK_START_RATE = "0.1"
python -c "import sys; sys.path.insert(0, 'device'); import device; [print(device.read_sensor()) for _ in range(30)]"
```
(env vars only affect a direct local run, not the Dockerized one — the container reads them from `docker-compose.yml`.)

**Tests (executed 2026-10-04):** `device/tests/test_device.py`, 7/7 passing. Each fault mode is tested deterministically by monkeypatching one rate to `1.0` at a time (not relying on true randomness) — covers: normal range, disconnect, error sentinel, stuck-episode repeat, plus `send_data()` success/exception/skip-on-disconnect.

**Regression check:** gateway (8/8) and cloud (5/5) tests still pass unchanged. `docker compose build device` succeeds.

**Measurement — fault-rate sanity check:** ran `read_sensor()` 2000 times with a fixed seed; observed roughly 2.5% disconnect, 1.65% sentinel, 4% stuck — consistent with the configured rates. Sample output showed smooth drift (e.g. `20.84 → 20.62 → 20.80 → 21.08`) with an occasional sentinel spike (`85.0`), matching the intended behavior.

## 4. Critical Evaluation & Maintenance

### `docker-compose.yml` fault rates drifted out of sync with `device.py` defaults
- **How discovered:** reviewing a manual edit to `device.py`'s default rates — `docker-compose.yml` still had the old values.
- **Problem:** `docker-compose.yml`'s explicit `environment:` values override `device.py`'s `os.getenv(..., default)` fallback, so the container was silently running different rates than the code's own defaults implied.
- **Fix:** synced `docker-compose.yml` to match (`ERROR_RATE=0.01`, `DISCONNECT_RATE=0.02`, `STUCK_START_RATE=0.03`).

## 7. Final Evaluation

- **Strengths:** device behavior now resembles a real DS18B20's known failure modes instead of pure uniform noise; the error-sentinel values the gateway was already tested against (v1.1.0) are now actually reachable from the simulated hardware; fault rates are configurable without code changes.
- **Weaknesses:** gateway/cloud still don't validate or flag sentinel values (85.0, -127.0 pass straight through, untouched since v1.0.0) — this version makes that gap reachable in practice, it doesn't close it.
- **Technical debt:** module-level mutable state (`_current_temperature`, `_stuck_reads_remaining`) is simple but not thread-safe — fine for this single-threaded loop, would need revisiting if the device ever became concurrent.
- **Risks:** nothing currently tracks or alerts on disconnect/stuck frequency from the outside (gateway has no idea the device went quiet) — if disconnect/stuck rates were misconfigured much higher, data loss would be silent from the cloud's point of view.
