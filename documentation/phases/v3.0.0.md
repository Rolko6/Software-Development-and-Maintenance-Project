# Documentation — v3.0.0 (Operations — Meaningful Metrics)

**Date:** October 5, 2026
**Author(s):** Roland Budzák
**Tool:** Claude (Claude Code)
**Scope of this version:** Close the metrics gap flagged repeatedly since v1.0.0 (cloud had zero metrics). Add Prometheus counters to cloud and extend gateway's with DS18B20 fault tracking. Deliberately *not* adding a Prometheus server or Grafana.

---

## 1. Overview

Every phase doc since v1.0.0 noted the same gap in its Final Evaluation: gateway had Prometheus counters, cloud had none. v3.0.0 closes that — cloud now exposes `/metrics/` with counters for secure-request success/rejection and legacy-endpoint usage; gateway gained a counter for DS18B20 sensor-fault sentinels. Deployment automation (CD, publishing to GHCR) was already built in v1.2.0, ahead of the original roadmap slot for it — so this version is metrics only.

---

## 2. AI-Assisted Development

### Is Grafana worth the complexity?

**Prompt:** "I was thinking about whether metrics + Grafana would be beneficial for Operations, or whether it would just unnecessarily complicate the system — what do you think?"

**Output:** Recommended against it. Grafana would mean a new service in `docker-compose.yml`, a Prometheus server to actually scrape and store the data, dashboards to configure and document — real added complexity for a course project that had consistently favored staying simple. "Meaningful metrics" (the assignment's actual wording) doesn't require visualization, just metrics that are useful. Recommended closing the cloud metrics gap first (small, matches the existing gateway pattern) and noting Grafana as a possible future step rather than building it now.

**Decision:** Accepted — no Grafana/Prometheus server added.

---

### Which metrics actually matter, and do we need tests for encryption too?

**Prompt:** "What metrics should we add so it actually makes sense — I was thinking test metrics, failed-data metrics, device behavior, encryption, etc. Also, how do I verify encryption works — do we need tests/metrics for that too?"

**Output:** Clarified a distinction: whether encryption *works correctly* is a testing question, already answered by the 33 tests from v2.0.0 (round-trip, tamper/wrong-key rejection, replay rejection), run automatically in CI. Metrics answer a different question — whether it's working *right now, live* — and "metrics for tests" isn't a sensible category (test pass/fail already lives in CI output). Proposed 4 concrete counters instead of a broad set: `secure_data_received_total`, `secure_data_rejected_total{reason}` (cloud), `legacy_data_received_total` (cloud), `sensor_fault_readings_total{type}` (gateway — cheap, since gateway already parses the temperature value). Explicitly left out device-side disconnect/stuck metrics, since device isn't a web server and giving it one just for metrics would be the same kind of complexity creep as Grafana.

**Decision:** Accepted, all 4 counters implemented test-first (Section 3).

## 3. Baseline Analysis

**What was added:**
- `cloud/app/metrics.py` (new) — `SECURE_DATA_RECEIVED_TOTAL`, `SECURE_DATA_REJECTED_TOTAL{reason}`, `LEGACY_DATA_RECEIVED_TOTAL`; `/metrics/` mounted in `cloud/app/main.py` (cloud had no Prometheus setup at all before this)
- `gateway/app/metrics.py` — added `SENSOR_FAULT_READINGS_TOTAL{type}`, incremented in `main.py` by matching the incoming temperature against the known DS18B20 sentinels (85.0 → `power_on_reset`, -127.0 → `crc_failure`)

**TDD cycle (executed 2026-10-05):** tests written first for all 4 counters, confirmed red (`assert 0.0 == 1`, `assert 404 == 200` for the unmounted `/metrics/`), then implemented. Final result: **cloud 24/24**, **gateway 18/18** (up from 19 and 14 — no regressions), **device 7/7** unaffected. 49 tests total across the project.

**Real verification on live containers:** `docker compose up --build -d`, then `curl http://localhost:8001/metrics/` — confirmed `secure_data_received_total 13.0` climbing as the device sent data through the gateway, and `legacy_data_received_total 0.0` (nothing hit the legacy path, as expected since gateway defaults to `/data/secure`).

## 4. Critical Evaluation & Maintenance

### A labeled counter with no observed label value yet prints no data line — looks broken, isn't
- **How discovered:** reading real `/metrics/` output from the running cloud container — `secure_data_rejected_total` showed its `# HELP`/`# TYPE` lines but no `secure_data_rejected_total{reason=...} <value>` line at all, since nothing had been rejected yet.
- **Problem:** this is normal `prometheus_client` behavior (a labeled time series is only created on first use of that specific label combination via `.labels(...)`), but reads as "the metric isn't working" to anyone not already familiar with the library's lazy-creation behavior.
- **Fix:** not a bug, nothing changed — documented here so it isn't mistaken for one later.

## 6. Operations

- **Build/test automation:** unchanged (CI now also runs `test_metrics.py` on both services automatically).

---

## 7. Final Evaluation

- **Strengths:** the cloud metrics gap flagged since v1.0.0 is closed; all 4 new counters map directly to real concerns already documented elsewhere (encryption health, replay attempts, legacy-endpoint bypass, sensor reliability); added with zero new infrastructure, test-first, no regressions.
- **Weaknesses:** nothing currently scrapes or stores these values over time — `/metrics/` only ever shows the current snapshot. No trend analysis, no alerting, until an actual Prometheus server is pointed at these endpoints.
- **Technical debt:** device remains unobservable from the outside — disconnect/stuck fault episodes (v1.3.0) still can't be seen in any metric, since nothing is sent to the gateway when the device is "disconnected" by design. Device logging is still unstructured `print()`.
- **Risks:** none introduced by this version specifically — the instrumentation is additive and low-risk (counters, no behavior change to the request/response paths they're attached to).
