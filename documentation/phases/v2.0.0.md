# Documentation — v2.0.0 (ML-KEM Integration)

**Date:** October 4, 2026
**Author(s):** Roland Budzák
**Tool:** Claude (Claude Code)
**Scope of this version:** Encrypt the gateway→cloud leg with ML-KEM-768 (FIPS 203) + AES-256-GCM. Device→gateway stays as-is (out of scope, per the original architecture comment in `cloud_client.py`).

---

## 1. Overview

v2.0.0 adds post-quantum key establishment to the one leg of the system that was always meant to get it (`gateway/app/cloud_client.py`'s "Later, this will become the place where ML-KEM is integrated" comment from v1.0.0). Every gateway→cloud request now does a fresh ML-KEM-768 encapsulation, derives an AES-256-GCM key from the shared secret, and encrypts the payload. The old plaintext `/data` endpoint stays for backward compatibility but is explicitly flagged as insecure whenever it's used. Built test-first: all tests were written and confirmed failing before any implementation existed.

---

## 2. AI-Assisted Development

### Design: library, key flow, legacy strategy

**Prompt:** "How would you design it so it's good, simply structured, as is customary in projects?" (continuing the pattern from v1.2.0's CI design question, applied to ML-KEM)

**Output:** `kyber-py` (pure Python, FIPS 203 ML-KEM, no native build toolchain) for the KEM; `cryptography`'s AES-256-GCM for the actual payload. Per-request encapsulation (no session state). Cloud keeps the old `/data` endpoint; gateway switches to a new `/data/secure` endpoint — explicit migration, not a silent swap.

**Decision:** Accepted.

---

### Security: which attacks matter here, and how to defend against them

**Prompt:** "It's important to secure ourselves against attacks — how do we do that?"

**Output:** Walked through the attack surface specific to this design and revised one part of the original plan:
- **Key distribution MITM** — the original plan (gateway fetches cloud's public key over `GET /public-key`) would let an attacker on the network substitute their own key. Fixed by pre-sharing the public key via `docker-compose.yml` at deploy time instead (same pattern as `CLOUD_URL`), so there's no live fetch to intercept.
- **Downgrade** — legacy `/data` stays open for compatibility, but every use logs a `WARNING` so it's never silent.
- **Replay** — a `timestamp` field inside the AEAD-encrypted payload (so it's authenticated, can't be forged), rejected by the cloud if older than a 30s window. Explicitly documented as a bounded, not absolute, mitigation — a full solution would need a server-side nonce cache, out of scope here.
- **Tampering** — AES-GCM's built-in auth tag catches any bit-flip in the ciphertext; a tampered KEM ciphertext decapsulates to a *different* shared secret (FIPS 203 "implicit rejection"), which then fails the same AES-GCM tag check downstream — one rejection path covers both cases.
- **Nonce reuse** — fresh random nonce generated every single encryption call.
- **Private key exposure** — the private key never leaves the cloud process; there is no endpoint that returns it, directly or indirectly.

**Decision:** Accepted all five mitigations; each became a specific test (Section 3).

## 3. Baseline Analysis

**Architecture (gateway→cloud leg only):**
```
gateway                                              cloud
  encapsulate(CLOUD_PUBLIC_KEY)                         |
    -> shared_secret, kem_ciphertext                    |
  AES-256-GCM encrypt(payload + timestamp)               |
    -> nonce, ciphertext                                 |
  POST /data/secure {kem_ciphertext, nonce, ciphertext}  |
                                                     decapsulate(PRIVATE_KEY, kem_ciphertext)
                                                       -> shared_secret
                                                     AES-256-GCM decrypt
                                                       -> payload
                                                     reject if timestamp > 30s old
                                                     store
```
Keys are pre-shared via `docker-compose.yml` env vars (`CLOUD_ML_KEM_PRIVATE_KEY` on cloud, `CLOUD_ML_KEM_PUBLIC_KEY` on gateway) — generated once, not fetched at runtime.

**TDD cycle (executed 2026-10-04):**
- Red: all new tests failed on collection with `ModuleNotFoundError: No module named 'app.crypto'`, on both services.
- Green, after implementation: **cloud 19/19**, **gateway 14/14** (33 total, including all pre-existing v1.0.0/v1.1.0 tests — no regressions). `device/tests` unaffected, 7/7.

**Test coverage, mapped to the attack table in Section 2:**
- round-trip correctness (`keygen`/`encaps`/`decaps`, AES-GCM encrypt/decrypt)
- wrong private key, tampered KEM ciphertext, tampered AES ciphertext, tampered nonce, wrong public key entirely — all rejected (400)
- stale timestamp — rejected (401)
- legacy `/data` — still works (200), logs a `WARNING`
- nonce uniqueness across repeated calls

**Real end-to-end verification (executed on live Docker containers, not just tests):** `docker compose up --build -d`, confirmed via `docker compose logs cloud` that requests arrive on `"Received data on secure endpoint"` (not the legacy path), and `GET /data` on the cloud returned correctly decrypted values matching what was sent.

**Latency measurement — comparison to v1.0.0 baseline:**
| | v1.0.0 (plaintext) | v2.0.0 (ML-KEM + AES-GCM) |
|---|---|---|
| `POST /device-data`, 5 sequential requests | ~8-26ms (variable) | ~19-20ms (consistent) |

ML-KEM encapsulation + AES-GCM adds roughly **8-11ms** per request on the gateway→cloud leg — confirms the expectation noted in v1.0.0's baseline doc.

## 4. Critical Evaluation & Maintenance

### `kyber-py`'s `encaps()` return order isn't what it looks like
- **How discovered:** manually running `ek, dk = ML_KEM_768.keygen()` then `ML_KEM_768.encaps(ek)` and printing byte lengths, before writing any test code against it.
- **Problem:** assumed `(ciphertext, shared_secret)` by analogy with other libraries; the real order is `(shared_secret, ciphertext)`. Printed lengths (32 vs 1088) caught the mismatch immediately — `ML_KEM_768.decaps(dk, 32-byte-value)` raised `ValueError: ciphertext type check failed. Expected 1088 bytes and obtained 32`.
- **Fix:** verified the real API against the installed library before writing `crypto.py`, not from memory/assumption.

### Docker build intermittently failed on a pip network timeout
- **How discovered:** `docker compose up --build` failed partway through `pip install` for the gateway image with `ReadTimeoutError: HTTPSConnectionPool(host='files.pythonhosted.org', ...): Read timed out`, which aborted the whole `up` (cloud/device never started even though their images were fine) — confusing from the outside, since Docker Desktop showed no containers at all.
- **Problem:** default pip timeout/retry settings aren't generous enough for a slow/unstable connection downloading `cryptography`'s wheel.
- **Fix:** `pip install --default-timeout=180 --retries 5 -r requirements.txt` in both `gateway/Dockerfile` and `cloud/Dockerfile`. Retried after the change, succeeded.

## 6. Operations

- **Build/test automation:** unchanged (CI from v1.2.0 now also runs the crypto test suites automatically).
- **Deployment:** unchanged — `docker compose up`. Keys must be present in `docker-compose.yml`/environment or the gateway/cloud containers fail to start (`KeyError` on missing env var, fail-fast by design).
- **Health checks:** unchanged.
- **Logs:** new `WARNING`-level log whenever the legacy `/data` endpoint is used, and whenever a `/data/secure` request is rejected (decryption failure or stale timestamp) — both include enough detail to investigate without leaking key material.
- **Metrics:** unchanged — gateway's Prometheus counters don't yet distinguish secure vs. legacy or track `/data/secure` rejections. Noted as a gap, not fixed here.

## 7. Final Evaluation

- **Strengths:** real post-quantum key establishment on the leg that mattered, test-first with a genuine red→green cycle, end-to-end verified on live containers (not just mocked tests), five concrete attack vectors each have a specific passing test, no regressions anywhere else in the system.
- **Weaknesses:** no metrics on `/data/secure` usage or rejection rate; legacy endpoint remains fully open to anyone who wants to bypass encryption entirely (logging is the only deterrent, not a technical control).
- **Technical debt:** 30-second replay window is a deliberate, documented compromise, not a complete solution; keys are committed in `docker-compose.yml` in plaintext base64, acceptable for a course project but would need a secrets manager in any real deployment.
- **Risks:** if `/data` (legacy) were ever exposed outside a trusted network, it bypasses all of this version's work with zero technical barrier; a sophisticated attacker that captures traffic within the 30s replay window could still successfully replay a request.
