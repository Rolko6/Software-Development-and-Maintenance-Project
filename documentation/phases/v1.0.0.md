## 1. Overview

v1.0.0 establishes the unencrypted baseline of the edge-cloud pipeline: a simulated legacy **device** sends temperature readings over plain HTTP to an **edge gateway**, which validates and forwards them to a **cloud** service that stores them in memory. The goal of this iteration was not to build a production system, but to get a simple, working, end-to-end reference implementation running — one that can be understood, tested, and measured before any security (ML-KEM) or operational hardening is added on top of it. Everything in this version was AI-generated and then reviewed, run, and verified manually (see Sections 2–4).

## 3. Baseline Analysis

**Architecture:**

```
device (Python script, no web server)
   │  POST /device-data   (HTTP, plaintext JSON)
   ▼
gateway (FastAPI, port 8000)
   - validates payload (device_id 1-100 chars, temperature: float)
   - increments Prometheus counters
   - logs device_id
   │  POST /data           (HTTP, plaintext JSON)
   ▼
cloud (FastAPI, port 8001)
   - validates payload (no length constraints — looser model than gateway's)
   - appends to an in-memory Python list (no persistence)
```
Services are wired together by `docker-compose.yml` via Docker's internal DNS (`http://gateway:8000`, `http://cloud:8001`); ports 8000/8001 are also published to the host for manual testing.

**How to run:**
```powershell
docker compose up --build -d
```
Starts all three containers in the background. `docker compose logs -f device` shows the simulated readings being sent every 5 seconds.

**Baseline tests (executed manually on 2026-10-04):**
- `GET /health` on gateway and cloud → both return `{"status":"healthy"}`, HTTP 200.
- `POST /device-data` with a valid payload → HTTP 200, forwarded to cloud, `{"status":"forwarded", ...}`.
- `POST /device-data` with an invalid payload (`device_id: ""`) → HTTP 422, rejected by Pydantic validation on the gateway before it ever reaches the cloud — confirms the gateway's validation layer works as intended.
- Full round trip confirmed: data sent by the `device` container appears in `GET /data` on the cloud service.

**Baseline measurements (executed manually on 2026-10-04, local Docker Desktop, no load):**
- `GET /health`: ~5-6 ms response time.
- `POST /device-data` → forwarded to cloud → response: ~8-26 ms per request (5 sequential requests), i.e. the full device→gateway→cloud→gateway→caller round trip.
- After ~1 hour of the `device` container running its 5s loop, `GET /data` on the cloud reported 400+ stored entries, confirming no data is silently dropped under normal (low-rate) load.
- These numbers are the reference point to compare against once ML-KEM key establishment/encryption is added in v2.0.0 — the expectation is a measurable latency increase on the gateway→cloud leg.

## 4. Critical Evaluation & Maintenance

Issues found by running the system and reading the code. None are fixed yet — tracked here for later versions.

### `/metrics` redirects instead of returning data
- **How discovered:** testing (`curl http://localhost:8000/metrics` → 307 redirect to `/metrics/`)
- **Problem:** Prometheus app mounted without trailing slash in `gateway/app/main.py`
- **Fix:** not applied yet

### Gateway and cloud validate data differently
- **How discovered:** code review (`gateway/app/models.py` vs `cloud/app/models.py`)
- **Problem:** gateway limits `device_id` length, cloud's copy of the same model doesn't — two separate models, no shared source of truth
- **Fix:** not applied yet

### Cloud storage grows forever and isn't persistent
- **How discovered:** code review of `cloud/app/storage.py` + observed 400+ entries after ~1h of the device running
- **Problem:** plain in-memory list, no limit, lost on restart (already flagged as a known shortcut in the code's own comments)
- **Fix:** not applied yet, intentionally deferred

### No authentication on any endpoint
- **How discovered:** code review
- **Problem:** anything that can reach port 8000/8001 can POST data under any `device_id`
- **Fix:** not applied yet — relevant for later, ML-KEM covers confidentiality, not auth

## 6. Operations

- **Build/test automation:** none yet — build and start is manual (`docker compose up --build`). No CI/CD pipeline.
- **Deployment:** local only, via Docker Compose on the dev machine.
- **Health checks:** `GET /health` on gateway and cloud, both return 200 (~5ms).
- **Logs:** gateway/cloud use Python `logging` (INFO level, device_id only); device uses plain `print()`. No log aggregation.
- **Metrics:** gateway exposes Prometheus counters (`device_messages_total`, `cloud_forward_failures_total`) at `/metrics/`. Cloud exposes no metrics.

---

## 7. Final Evaluation

- **Strengths:** clean device/gateway/cloud separation, small readable codebase, verified working end-to-end, Dockerized, basic health checks and metrics already in place at the gateway.
- **Weaknesses:** no encryption or authentication anywhere, no automated tests, duplicated/inconsistent validation between gateway and cloud, cloud has no metrics.
- **Technical debt:** in-memory-only storage (flagged in code as temporary), duplicated `SensorData` model, no retry/backoff on transient failures.
- **Risks:** data loss on restart (storage), sensor data travels unencrypted (motivates ML-KEM in v2.0.0), unbounded memory growth under sustained load, no auth means any caller can inject fake readings.

Testing (v1.1.0) is scheduled before CI (v1.2.0) on purpose — a pipeline that automates nothing yet is pointless. v3.0.0 is scoped narrower than the assignment's "Operations" bullet to avoid repeating v1.2.0's CI work; it only adds what's still missing after that: deployment automation and the observability gaps noted in Section 4/6 (no cloud metrics, no structured device logging).

**v1.1.0 — testing approach:** per-service `tests/` folder (consistent with the v1.0.0 decision to not use a root-level `tests/`), using `pytest`:
- **gateway:** FastAPI `TestClient` against `/device-data` and `/health`; mock `send_to_cloud` (e.g. `unittest.mock`/`respx`) so tests don't need a real cloud running — cover valid payload, invalid payload (422), and cloud-unreachable (502).
- **cloud:** `TestClient` against `/data` and `/health`; unit tests for `storage.py` directly (pure functions, no mocking needed).
- **device:** unit tests for `generate_sensor_data()` (value range/type) and `send_data()` with `requests.post` mocked — both success and `RequestException` paths.
