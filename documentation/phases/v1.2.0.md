# Documentation — v1.2.0 (CI/CD Pipeline)

**Date:** October 4, 2026
**Author(s):** Roland Budzák
**Tool:** Claude (Claude Code)
**Scope of this version:** Add a GitHub Actions pipeline that runs the v1.1.0 tests, verifies the Docker build, and publishes images to GitHub Container Registry (CD) on pushes to `main`.

---

## 1. Overview

v1.2.0 adds CI/CD on top of the v1.1.0 test suite — no production code changed. On every push/PR, the three services are tested independently and the Docker build is verified. On pushes to `main`, built images are also published to `ghcr.io`, giving the team a way to pull a known-working version without building from source.

---

## 2. AI-Assisted Development

### CI pipeline design

**Prompt:** "How would you design this so it's good, simply structured, as is customary in projects?"

**Output:** GitHub Actions (`.github/workflows/ci.yml`), triggered on `push` and `pull_request`. Four independent jobs: `test-device`, `test-gateway`, `test-cloud` (one per service, not combined — see Section 4 of v1.1.0 for why), and `build` (runs `docker compose build` to catch broken Dockerfiles). `build` has no `needs:` dependency on the test jobs so it runs in parallel and gives faster feedback.

**Decision:** Accepted as-is.
---

### Verifying `publish` without touching `main`

**Prompt:** Current work happens on a feature branch that is a full rewrite of what's on `main`; merging now would be nothing but conflicts, and `main` is not being touched until the rewrite is finished. Question: how to verify the `publish` job without pushing to `main`?

**Output:** temporarily widen the `if` condition to also allow the current feature branch, push, confirm the job runs and images appear in GitHub Packages, then revert the condition back to `main`-only.

**Decision:** Accepted. Applied temporarily, verified (see Section 3), then reverted.

---

## 3. Baseline Analysis

**How to run:** push to GitHub — the workflow runs automatically (not something you run locally). `.github/workflows/ci.yml` is the single source of truth for what runs.

**Test results (executed on GitHub Actions, 2026-10-04):** all 5 jobs passed on the feature branch (with the `publish` condition temporarily widened to verify it end-to-end):
- `test-device`: 9s
- `test-gateway`: 10s
- `test-cloud`: 11s
- `build`: 24s
- `publish`: 41s — confirmed `gateway`, `cloud`, `device` images appeared under the repository's **Packages**

**Notes:** GitHub flagged 5 deprecation warnings (Node.js 20 runtime used by `actions/checkout@v4`, `actions/setup-python@v5`, `docker/login-action@v3` — GitHub is moving these to Node 24). Non-blocking today; tracked as technical debt (Section 7) to bump action versions later.

---

## 4. Critical Evaluation & Maintenance

### `publish` can't be tested on `main` without disrupting an unfinished rewrite
- **How discovered:** `main` currently holds a different, older version of the project; the current work is a full rewrite happening on a feature branch, not yet ready to merge.
- **Problem:** the `publish` job's trigger (`if: ... refs/heads/main`) meant it would never run until merged — but merging early would create large conflicts and wasn't the goal yet.
- **Fix:** temporarily broadened the `if` condition to include the feature branch, verified `publish` works, then reverted it back to `main`-only. No permanent workaround needed — this was a one-time verification step.

## 6. Operations

- **Build/test automation:** automated via GitHub Actions on every push/PR (`test-device`, `test-gateway`, `test-cloud`, `build`).
- **Deployment:** `publish` job builds and pushes `gateway`/`cloud`/`device` images to `ghcr.io` on pushes to `main`. No automatic "running" of those images anywhere yet — pulling and running them is still a manual step for whoever wants the latest tested version.
- **Health checks:** unchanged from v1.0.0.
- **Logs:** unchanged from v1.0.0. CI step output itself is viewable per-job in the GitHub Actions UI.
- **Metrics:** unchanged from v1.0.0.

---

## 7. Final Evaluation

- **Strengths:** every push is now automatically tested and build-checked; `main` will always have a corresponding published, working image once this reaches `main`; verified end-to-end on real GitHub Actions infrastructure, not just locally.
- **Weaknesses:** `publish` only builds/pushes images — nothing automatically deploys or runs them anywhere; that gap is intentional for now (no shared server) but is a known limitation.
- **Technical debt:** pipeline actions use versions GitHub is deprecating (Node 20 runtime) — should be bumped to current major versions before they stop working.
- **Risks:** anyone merging into `main` without running CI locally first could introduce a regression that only surfaces once pushed — acceptable since CI catches it immediately and nothing auto-deploys from a broken state.
